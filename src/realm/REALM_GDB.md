# realm-gdb.py: Realm user threads in gdb

`realm-gdb.py` is a gdb extension, in Python, that shows gdb the stacks of Realm's user threads. librealm embeds it in its `.debug_gdb_scripts` section (in Debug and RelWithDebInfo builds on ELF platforms), so gdb loads it with the library. This note describes what it does, why, how it is tested, and what it can't do.

**The problem.** Realm can run tasks on *user threads* (`Realm::UserThread`): contexts it switches in and out of the program's kernel threads with `swapcontext`. A user thread that is *running* is just the stack of the kernel thread it runs on, which gdb shows as it shows any thread. One that is *parked* (waiting, with its registers saved in its `UserThread::ctx`) runs on no thread, so gdb has no way to show its stack, though in a hang the interesting stacks are often there. realm-gdb finds the user threads in Realm's registry (`Realm::user_thread_registry_head`) and shows the parked ones: in a live process, started by gdb or attached to, and in a core file.

**The design space.** A parked user thread's stack can be shown to gdb in two ways:

- **Unwinding into it.** A Python unwinder claims a stopped thread's innermost frame and reports the parked thread's saved registers as that frame's caller's, so the parked stack appears above it. Nothing in the program changes, but gdb then prints and evaluates a stack it didn't unwind itself, through a frame that isn't really part of it (§2.1). An earlier design did this everywhere. realm-gdb does it in core files, which can't be written (§4).
- **Writing its registers.** The parked thread's saved registers are written into a stopped thread, which then *is* the parked thread as far as gdb can tell, until its own registers are put back. gdb unwinds, prints and evaluates it natively, function calls included (§2.2). But the program has been changed, and must not run, or be let go of, until it is put back (§2.3). realm-gdb does this in a live process, for the length of one command at a time, which is what makes it safe (§3).

The requirements, in priority order, which every choice here weighs against:

> (a) not crashing/corrupting memory (this includes running functions that may read or write garbage values), (b) not confusing the user by showing unrelated information (e.g., by showing frames from another thread), (c) or at the very least printing a message to indicate what is or isn't being shown that may be unexpected.

**Terms** used throughout:

- **user thread**, **running**, **parked**: as above. Realm marks a parked user thread with `UserThread::running` false.
- **host**: the stopped thread (one of gdb's threads) that shows a parked user thread.
- **register window**, or **window**: a parked user thread shown on a host by writing its saved registers into the host, for the length of one command, then putting the host's own back (`_Window`, §3.1).
- **view**: a parked user thread shown on a host by the unwinder, in a core file (§4); there the **host frame** is the host's innermost frame, which the unwinder makes unwind into the parked thread's context.
- **selection**: a parked user thread recorded by `realm-thread N`, until `realm-thread back`; in a live process it changes nothing in the program (§3.8).
- **hooks**: gdb runs a user-defined `hook-COMMAND` before COMMAND, and `hookpost-COMMAND` after it. realm-gdb defines them for the commands it must refuse in a window, or show a selection to, each running its `realm-gdb-guard` (§3.6, §3.9); those are the **hooked commands**.
- **plain commands**: gdb's own commands typed as usual (`bt`, `print VAR`), which, while a parked thread is selected, show it through their hooks (§3.9); as against **`rt COMMAND`**, which runs COMMAND on the selected parked thread explicitly, in any session.
- **the parked section**: what `thread apply all bt` prints after gdb's own threads, the backtrace of each parked user thread, between lines of its own ("=== Parked Realm user threads ... ===").
- **dummy frame**: the frame gdb pushes for a function call it makes in the program (`print f()`); a window's calls run on the parked thread's stack (§3.3).
- **unrestored**: a host whose own registers a window couldn't put back; realm-gdb then keeps the program from running (§3.6).

Function names refer to `realm-gdb.py`, test names to `tests/gdb/realm_gdb_tests.py` (`terminal.NAME`: `tests/gdb/run_realm_gdb_terminal_tests.py`). "gdb N" means upstream gdb major version N.

## 1. The decision

| Target | How a parked user thread is shown |
|---|---|
| Live process, all-stop mode, every thread stopped | A **register window**: the parked thread's saved context is written into a stopped thread's registers for the duration of *one command*, and that thread's own registers are put back before the command returns. |
| Core file | A **view**: a Python unwinder makes the host's innermost frame unwind into the parked context (§4). |
| Non-stop mode, a running program, record/replay | Not shown. Every command that would show one says why and how to see it. |

The commands:

- **`thread apply all bt`**, in any spelling and with any bt options and `thread apply` flags, works as before, and adds a section for the parked threads. In a live process each parked thread's backtrace comes from a register window.
- **`realm-thread`** lists the user threads, numbered as `info threads` numbers gdb's.
- **`realm-thread apply N...|all COMMAND`** runs any command on parked threads, given as `thread apply` takes an ID list (numbers, ranges, pointers), or on each of them in turn: `bt full`, `frame apply level 3 print VAR`, `info locals`, and so on.
- **`realm-thread N`** (or a `UserThread` pointer) selects a parked thread, and **`realm-thread back`** goes back to the previous selection; selections nest. The effect depends on the target:
  - **In a live process** it only records the selection, in Python. **`rt COMMAND`** then runs `COMMAND` on that thread in a register window, starting from the frame last selected on it, so `rt frame 3` followed by `rt print VAR` works (§3.8). In a console session, plain `bt`, `frame N`, `print VAR` and the like do the same through gdb's command hooks, and commands that would act on the host thread as it really is are refused (§3.9).
  - **In a core file** it keeps the parked stack shown by the unwinder until `back`, so plain `bt`, `frame N` and `print` work on it. `rt COMMAND` is just `COMMAND` there, but for the commands that read the lines after them, refused as in a live process (`core_body_commands`).

Nothing of a parked thread stays shown in a live process between commands: once a command is over, the program is exactly as it was. The exception is a plain command that fails: its window stays open until the next prompt or hooked command, which only makes a difference without a prompt (`-ex` sequences, scripts, Python that catches the error; §3.9, §8.3). At gdb's prompt, nothing has changed.

## 2. Why

### 2.1 What the unwinder costs

The unwinder approach never changes the program, but gdb then has to print and evaluate a stack it didn't unwind itself, through a host frame that isn't really there. In an earlier design, which used it in live processes too, that was the cause of most of the complexity and most of the open issues:

- **The marker line** (§4). Frame #0 is another task's frame, so it is drawn as a marker, and the marker forces gdb's Python frame printer. That printer differs from gdb's own printer:
  - it lists locals differently;
  - it loses frame numbers after a call;
  - before gdb 13 it reads freed memory after a call;
  - it hands entirely optimized-out values to pretty-printers.
- **Calls refused while printing,** to keep the Python frame printer from reading freed frames. So a pretty-printer that calls a function, as libstdc++'s do for some types, prints raw with a note. gdb 8 can't refuse calls, so there the marker is dropped instead.
- **Frame #0's values are wrong** while a view is shown (§4). A pretty-printer can then run calls on garbage, which is an (a) problem as well as a (b) one.
- **Callee-saved floating-point registers** (aarch64 d8–d15) aren't supplied, so their values show as `<optimized out>`.
- **Keeping persistent views safe** needed a lot of machinery:
  - *doomed* views, dropped only once gdb had found its selected frame again, as gdb 11–13 abort if it can't;
  - undoing a *forced return*, MI's `-exec-return` from a parked frame (which writes the host's registers), which can't be done before gdb 11;
  - events posted to do that work once a command was over, and with them a workaround (`__cxa_atexit`) for gdb ≤ 14, which crashes as it exits with one left;
  - a parameter, `realm-lock-calls`, to hold the other threads during function calls;
  - the arming scheme for gdb < 11 (§4).

### 2.2 What register writes buy

With the parked context in a real thread's registers, gdb unwinds, prints and evaluates the parked stack exactly as it would a running thread's:

- frame #0 is the parked frame, and `bt N` and `set backtrace limit` count naturally;
- gdb's own printer is used, so "No locals." lines and artificial locals appear, and optimized-out values are handled natively;
- pretty-printers that call functions work, with every frame numbered;
- every callee-saved register is right, aarch64's d8–d15 included (`apply_callee_saved_fp` passes in CI's aarch64 jobs, live and attached);
- there is no wrong frame #0, because the host's own frames aren't in the chain.

It also avoids four bugs of an earlier version's register-writing code, which kept a parked thread's registers in place across commands (§2.3):

- **Only some registers.** It wrote only rip/rsp/rbp, so values held in callee-saved registers showed the host's. `hot0`/`hot1` were silently wrong on gdb 9.2.
- **An ineffective call swap.** It put the host's registers back for function calls, but gdb computes the call's stack pointer and saves the caller's state before Python hears about the call (`inferior_call_pre`). So the calls ran on the parked stack anyway.
- **A mixed state after a stopped call.** When a call stopped, it rewrote rip/rsp/rbp over the stopped call's state.
- **The wrong command.** Its parked section always ran plain `bt`, whatever command the user gave.

### 2.3 Why not a persistent register-write view

A parked thread shown with register writes *across* commands, as that earlier version did, can't be made safe. Every path that resumes the program, detaches from it or ends gdb has to put the registers back first, and several such paths give Python no chance to:

| Path | What happens with a view still shown |
|---|---|
| MI `-exec-continue`, an IDE's Continue button | The only pre-resume event is `gdb.events.cont`. gdb's `proceed()` has already fetched the thread's regcache, and writing any register (`value_assign` → `target_changed` → `registers_changed`) frees every regcache, which `proceed` then uses. This is a use-after-free on every gdb from 8.2 to 17.1. gdb 16.3 segfaulted on it, and a CLI run survived only by luck. |
| MI `-target-detach` | No gdb exposes a pre-detach hook to Python; `inferior_pre_detach` (gdb ≥ 14) is internal. The program died after detach: "Assertion `switch_to->running == false' failed", then "stack smashing detected". |
| `gdb -batch` ending, MI `-gdb-exit` | gdb < 12 has no `gdb_exiting` event. Corrupted on 9.2. |
| SIGTERM to gdb | On gdb 12–13 the quit flag is still set, so Python raises KeyboardInterrupt on entry to the `gdb_exiting` handler, before any of its code runs. Corrupted on 9.2 and 12.1. |
| kill -9 of gdb | Corrupted on every version. |
| Telling MI sessions apart | Not reliable: a secondary MI `new-ui` can sit behind a console. The unwinder design's attempt at it failed for that reason. |

Confining the register writes to one command removes all of these but gdb dying. Nothing outside gdb can run in the middle of a command, so the remaining paths are commands run *inside* the window, which are refused (§3.6), and another UI's commands during a function call, which gdb lets run then, and which realm-gdb avoids by refusing calls while a second UI may be open (§3.4). What gets past the refusals is stopped before it runs where it can be, and gdb dying kills an attached program on Linux rather than leave it corrupted (§3.7).

## 3. Register windows

### 3.1 Life of a window (`_Window`)

1. **Keep the host's registers.** `_snapshot_names` takes the `save` register group (gdb ≥ 10): everything gdb itself keeps around an inferior call, floating-point and vector registers included. Older gdbs use `_Arch.fallback_regs`: the same registers, those that gdb has, listed by hand. On x86-64 that is the general, segment, x87, SSE/AVX/AVX-512 and mask registers, `mxcsr`, `pkru`, `fs_base`, `gs_base` and, on Linux, `orig_rax`. `orig_rax` decides whether the kernel restarts an interrupted system call, and gdb sets it while a function call runs; a call that never returned would leave it changed. (Writing `$rip` with `set var`, as a window does, leaves it alone.)
   - **gdb 8.2 can't write a vector or x87 register from a Python value,** so there a window keeps a copy of each in a gdb convenience variable (`$_realm_gdb_saved_0_xmm1`, `_keep_in_gdb`) and assigns it back. The number is the window's, so that a later window doesn't overwrite the copies of one that couldn't put its registers back (§3.6).
   - **realm-gdb's own expressions and register writes are parsed as C++** (`_CLanguage`), whatever the language: Pascal and Ada take `set var $r12 = 0x10` for a comparison and write $r12 another value, without an error, and Pascal, Ada, Modula-2, D and Go don't find `Realm::user_thread_registry_head` (`window_language`, which also sets Pascal from inside a window).
   - **Its own numbers are written so that `set input-radix` doesn't change them:** in hex, as C++, for the settings a window sets and puts back and for its register writes; in the input radix, for the count it adds to a core-file view's `bt N`. Read in radix 16, a decimal 10 would set the call timeouts to 16, which the window wouldn't then recognize as its own, and the check of the extended registers would write a number too large and take the error for AMX (`window_input_radix`, `core_input_radix`).
   - **Settings that change how registers are read** don't keep the window from putting them back. `max-value-size` below a register's size (`rt set max-value-size 16`, under an AVX-512 register's 64 bytes) is raised while realm-gdb reads or writes them (`_BigValues`, `window_max_value_size`). `set endian`, `set tdesc filename`, `set architecture` and `set osabi` are refused in windows (§3.6).
   - **realm-gdb's own register writes skip realm-gdb's own checks** (`_internal`), though a user's own `set hook-variable` still runs for each (about thirty in a window). Only that command is exempt: another run meanwhile (by another extension's `register_changed` handler, say) is still guarded (`window_internal_bypass`), and one that starts a program refused (`window_nested_external`). Run as the user's are, each write would get a plain command's window of its own while a parked thread is selected (§3.9), and `realm-thread back` could never put back a window's leftovers.
2. **Write in the parked context.** `_Arch.context_regs` is written in frame #0 (§3.2).
3. **Run the command, capturing its output** (`gdb.execute(..., to_string=True)`, through `_execute`, which decodes gdb 18's MI stream records, §3.6). On gdb ≥ 10 it runs with Ctrl-C let through (§3.4).
4. **Pop any of the window's calls left stopped** (§3.3), then **put back** every kept register whose raw contents differ, until none do (`_put_back`).
   - One that can't be read or written doesn't keep the others from being put back, and the warning quotes gdb's error (§6.5, on gdb 13 and AMX).
   - Bits that the kernel keeps itself are left out of the comparison (`_Arch.kernel_bits`, `_same_reg`): aarch64's PSTATE.SS in `cpsr`, which a signal that cut a single step short leaves set, as when a host is stopped before it runs (§3.7), and which can't be written back as it was read.
   - A KeyboardInterrupt is retried, ten times; a thread left half restored even so is listed as unrestored (§3.6). Ctrl-C is blocked in windows but for their calls and commands, and held in realm-gdb's own code (§3.4), so this is left to one taken by another thread where realm-gdb can't see such threads (off Linux). One that lands before `close` has done anything leaves the window open, its guards still refusing, for the next prompt, never inside a window, to close (`window_close_interrupted`, `window_left_open`; from gdb 15, gdb's event loop, `window_left_open_mi`: §3.9).
   - Comparing everything, rather than just what the window wrote, also undoes register changes made inside the window: `set $rbx = ...`, `set $pc = ...`, or MI's `-exec-return` from Python.
5. **Reselect** the thread and frame the user had selected, and print the captured output. If the host stopped at the start of inlined functions that gdb showed as not entered yet, gdb now shows them as frames: the same frame stays selected, and a note says so (§8.4).

One window can show several parked threads in turn: `thread apply all bt` and `realm-thread apply all` keep the host's registers once and write each context over the last. Measured times were 9–19 ms for one parked thread and 38–53 ms for all seven in the test program, on gdb 9.2, 12.1 and 16.3.

- **Other register changes carry over** from one parked thread's command to the next: a register the context doesn't hold (`$ymm0`'s upper half, say) keeps what a command set it to until the window closes. The "doesn't last" note is printed for the first command that changed it only.
- **A command that selects another thread or inferior** (`realm-thread apply all thread 2`, Python's `InferiorThread.switch()`, `inferior N`) leaves the window on the host: the host is selected again before the next parked thread is shown, and before its registers are put back (`_Window.to_host`). Else the next context would go into a thread whose registers the window never kept, and the program would abort when continued (`window_apply_switches_thread`).
- **Each parked thread is checked again** before it is shown (`_parked_problem`), as the last one's command may have changed it. If that command began recording (every command that can is refused, §3.6), the rest aren't shown, as recording would log their contexts being written in (`apply_recording_began`).

A window opens only in all-stop mode, with every thread stopped (`_how_shown`), and `_Window.__enter__` refuses to nest. As it opens it checks that realm-gdb's hooks are in place, that no `with` around the command has changed a setting it can't open under, and that no earlier window left the host's own registers unrestored (§3.6).

### 3.2 What the context holds

| Platform | Registers written | Notes |
|---|---|---|
| Linux x86-64 | rip, rsp, rbp, rbx, r12–r15, rdi, rsi, rdx, rcx, r8, r9 from `gregs[]`; rax = 0 | getcontext() saves these. No SSE register is callee-saved in the SysV ABI. |
| Linux aarch64 | x19–x30, sp and pc from `regs[]`; x0 = 0; v8–v15 from the `fpsimd_context` record at the start of `uc_mcontext.__reserved` | glibc's `swapcontext` stores q8–q15 whole at `vregs[8..15]` (offset 16 + 16n), after a header with magic `FPSIMD_MAGIC`. Checked in glibc 2.35 and master. With recent glibc the saved PC is a stub, `mov x30, x1; ret`, and the real return address is in x1. `_returns_to_x1` recognizes the stub, as on the other branch. |
| FreeBSD x86-64 | the same registers, from the `mc_*` fields | Tested in CI (FreeBSD 15.1), and on 14.5 in a VM here. FreeBSD's `swapcontext` is a system call, so the context is saved inside libc's `_swapcontext` stub, called from libthr's `__thr_swapcontext`: frame #0 is the stub's, as for any thread there blocked in a system call, and `user_switch` is #2 (§8.9). |
| FreeBSD aarch64 | x19–x30, sp, pc; v8–v15 from `mc_fpregs.fp_q[]` if `_MC_FP_VALID` | Untested. |

- **Registers the context doesn't hold** keep the host's values. Those are caller-saved registers, dead at the resume PC, which is just after a call.
- **The floating-point control state** (the x87 control word and MXCSR's control bits on x86-64, FPCR on aarch64) is callee-saved, and the context holds it (glibc's `__fpregs_mem.cwd` and `mxcsr`), but a window doesn't write it: the host's stays. So a call in a window runs with the host's rounding mode and exception masks, and `info registers mxcsr` shows the host's. They differ only if the program changes them (`fesetround` in a task, say).
- **The flags and the x87 stack** (eflags, with its direction flag, and the x87 registers and tags on x86-64) are the host's too, which a window's calls inherit, as gdb's own calls on that thread do. That matters only if the host stopped in the middle of a backward string copy, or with values on the x87 stack (unverified).
- **Thread-local storage** (fs_base on x86-64, tpidr on aarch64) is also the host's. That is so in a core file's view too. The dump's header says whose thread-local variables are shown.
- **If the FP record can't be read,** realm-gdb prints a note saying that d8–d15 show the selected thread's values.
- **SVE.** On SVE hardware, writing v8 clears the rest of z8. The `save` group should hold z8–z15 as raw registers, and the fallback list names them, so `_put_back` should restore them exactly. This is untested.

### 3.3 Function calls in a window

A call made in a window runs on the host with the parked thread's registers, so it runs on the parked thread's stack, just below its saved SP. gdb takes the call's stack pointer from frame #0 before it notifies Python, so nothing can move it. That memory is unused while the thread is parked. These settings are in force for the window's calls, and the user's own values are put back afterwards (`_CallSettings`):

| Setting | Why |
|---|---|
| `scheduler-locking on` | Realm can resume a parked thread on *any* thread: `user_switch` sets `host_pthread = pthread_self()` on resuming. So any other thread that ran during the call could resume the parked thread onto the stack the call is using. |
| `unwindonsignal on` | gdb reads it only *after* it notifies `inferior_call_post`, as the 8.2, 12.1 and 17.1 sources show, so it has to stay on for the whole window. Without that, a faulting call is left on the parked stack; putting the host's registers back then abandons it with the signal still pending, and the program died of SIGSEGV after detach. |
| `unwind-on-terminating-exception on` | A C++ exception escaping the call is unwound too. |
| `direct-call-timeout` / `indirect-call-timeout` 10 s, `unwind-on-timeout on` (gdb ≥ 15) | A hung call is unwound. A lower value set by the user is kept. realm-gdb stops a call itself where these don't (below). |
| `stop-on-solib-events 0` | A call that loads a library (`dlopen`) would otherwise stop at the event, and be abandoned holding the dynamic loader's lock: the program then hung in `exit()` (`window_solib_events`). |
| `may-insert-breakpoints on` | The breakpoint that stops a refused call (below) needs it, and so does the call's own return. |
| `follow-fork-mode parent` | A call that forks would otherwise have gdb follow the child, and detach from the parent, whose host has the parked thread's registers, in the middle of the call. |
| `detach-on-fork on` | With `detach-on-fork off`, gdb would keep a forked child stopped, a copy of the program in the middle of the call, and a call that waits for it (`system()`) would stop there, and be abandoned (`window_fork_call`). |
| `confirm off` | See §3.4. |
| `multiple-symbols all` | gdb's menu for an ambiguous location (`break` of an overloaded function, with `set multiple-symbols ask`) reads the terminal itself, which `confirm off` doesn't answer: in `rt` its question would be collected, unseen, while gdb waited (`window_multiple_symbols`). gdb itself answers "all" under MI. |
| `maint set internal-error quit no`, `internal-warning quit no`, their `corefile no`, `demangler-warning quit no`; `internal-error backtrace off`, `internal-warning backtrace off` (gdb ≥ 12) | See §3.4. They aren't gdb parameters, so they are read from `maint show`. |
| `may-call-functions off`, only while a parked thread with under 64 KiB of free stack is shown, or in every window if gdb can't write the extended registers or a second UI may be open (gdb ≥ 9), or on a host a syscall catchpoint stopped | See below, and §3.4. |

- **The five that matter only while a call runs** (`scheduler-locking`, `stop-on-solib-events`, `may-insert-breakpoints`, `follow-fork-mode`, `detach-on-fork`) are set as the window's call begins (`inferior_call_pre`) and put back as it ends, so that a command in the window sees the user's: the gdb manual's idiom that saves `$_gdb_setting_str("scheduler-locking")`, changes it and sets it back, run with a parked thread selected, would otherwise leave `scheduler-locking on` for good (`plain_gdb_setting`). The others are in force for the whole window: gdb reads `unwindonsignal` and `unwind-on-timeout` once the call is over, and queries and the pager can come anywhere in the command.
- **A command in the window can change them** (`with scheduler-locking off -- print f()`, a user-defined command, Python), so just before each call `_CallSettings.for_call` puts back any that differ, and a note says so: with scheduler-locking off the other threads ran during the call and the program crashed with SIGSEGV, and with unwindonsignal off a faulting call was left on the parked stack, its signal pending (`window_settings_kept`). A `with` around a plain command sets its setting before the window opens; hook-with notes the window's settings as it begins (`_with_hook`), so that such a change is overridden for the calls too, and noted. A change a command makes to one of the five outlasts the window, as it would without one.
- **A setting is put back only if it still has the window's value:** otherwise something changed it since, and the window leaves it. `with`, `maintenance with`, and `set` of each setting a window changes (`_WINDOW_SETTINGS`) close a failed plain command's window first (§3.9). Else, after a failed plain command, `with scheduler-locking off -- print 1` would save the window's `on` and put it back once the window was gone, and the user's own `set confirm off` would be undone as the window closed (`plain_failed_settings`); and a failing `with scheduler-locking step -- print X` would have the window, closing after `with`, put back the `step` it had found (`plain_failed_with`).

**Other safeguards for calls:**

- **Breakpoints of every kind are disabled while a call runs** (`_on_inferior_call`, `_disable_breakpoints`): a call that stopped at one would be left on the parked stack. A note says so, once for the same breakpoints, and only for calls that ran, not for refused ones (below), told by their entry points (`refused_pcs`). They are put back as they were: hit counts don't change, and an enable count (`enable count N`), which enabling a breakpoint drops, is set again (`window_breakpoint_in_call`, `window_breakpoint_kinds`).
  - **Those Python doesn't see** are disabled by number, from `info breakpoints`, read at annotation level 0 (`_breakpoint_table`, `window_annotate`): dprintfs on every gdb, and before gdb 11 catchpoints and hardware breakpoints. No version is checked. A call stopped at a system-call catchpoint would be abandoned in the middle of the system call, which putting the registers back doesn't undo: on x86-64 the host would stop again at once where it had stopped, and on aarch64, which has no register for the system call's number, make the call when resumed with its own registers as arguments (`window_catchpoint_in_call`).
  - **A breakpoint made during the call,** by Python code that runs meanwhile (another extension's handler of `inferior_call`, say), is disabled as it is made (`_on_breakpoint_created`, `window_call_new_breakpoint`), but for the one that stops a refused call.
  - **Watchpoints on the host's own frames are lost** to a call nonetheless: as the call resumes the host, gdb checks every hardware watchpoint set on a frame of that thread, disabled or not, looks for its frame among the frames the host has then, the parked thread's, and deletes the watchpoint at the next stop ("Watchpoint 2 deleted because the program has left the block"). realm-gdb can't stop that; it names them afterwards, and says that `watch -l`, which has no frame, isn't affected (`window_watchpoint_lost`). A watchpoint on another thread, or on a global, is kept.
  - **Python `FinishBreakpoint`s on the host's frames are lost** the same way to a call that stops (one the window refused, let through, below): gdb deletes them at the stop, silently. realm-gdb notices that a breakpoint it disabled is gone, and says so, naming one made with `internal=True` as internal (`window_finish_breakpoint`). An internal watchpoint made from Python isn't in `info breakpoints`, so its loss isn't noted.
  - **The script loaded again during a call** (by the embedded copy in a library the call loads) keeps what the window disabled, and the count of calls in progress (`window_reload_in_call`).
- **A call that fails before it runs** (it can't write its stack, with `may-write-memory off`; too few arguments, on gdb 8) gets no `inferior_call_post`. Its breakpoints would stay disabled and the count of calls in progress up, so that a script's `continue` would run past them. A window puts them back as it closes, as no call made in it can be running then (`window_call_failed_early`); a count such a call left outside any window, with no prompt after it (a script, MI), is dropped as the next window opens, once no call is in progress (`_call_running`, `window_call_failed_outside`).
  - **Whether a call is in progress** can't be told from whether a thread runs: gdb pretends the program doesn't run during a call (`is_running()` is false). The selected thread tells it: gdb won't read the registers of a thread running a call ("Selected thread is running"), and one stopped in a call (at a dprintf, or between its stop and gdb's `inferior_call_post`) has the call's dummy frame. That dummy frame must be a counted call's: the frame just older than it must be the thread's newest as gdb sent `inferior_call_pre` (`_note_call_start`); a second call from the same frame marks the first as over. So a call of the user's left stopped on the host doesn't keep up a failed call's count (`plain_call_left_stopped`), and a dprintf hit in a call made outside any window doesn't open a window for its `printf` in the middle of the call (`plain_dprintf_in_call`). A window's calls are counted from the count it opened with.
  - **Inside a window,** such a count is dropped as each command run there ends (`_calls_over`), and between commands once the thread the window's last call was made on has no dummy frame it didn't have as that call began (`_calls_left_up`); else a failed plain command's window would stay open through the hooked commands after it (`plain_call_failed_early`). Within one command (a script that catches the failed call's error and carries on), the count stays up until a hooked command, a window or the prompt checks it.
- **A call left stopped** nonetheless has its dummy frame popped (`_Window.pop_calls`, by a `return` the guards ignore), after the command of the parked thread it was made on, before the next one is shown and before the registers are put back (`window_abandoned_calls`). That puts back gdb's state of the thread from before the call (where and why it stopped, its pending signal), and drops the call's own breakpoint, which on x86-64 gdb puts just below the call's stack pointer, in the parked thread's stack (on aarch64, at the program's entry point), and would otherwise insert there whenever the program ran, writing back what it had saved of that memory at each stop; unpopped, the host would also stop again at once at that breakpoint, and get the signal the call stopped with.
  - **gdb's frame cache is reset first** (`gdb.invalidate_cached_frames`, not while a call is in progress). Two quick Ctrl-Cs, one stopping the call with SIGINT and the next quitting gdb as it handles that stop, leave the frame cache cut short at frame #0, which hides the call's dummy frame. Under a SIGINT every 3–30 ms, without the reset, 6 of 6 runs on gdb 12.1 left a call that couldn't be popped (3 of 3 on 11.2, 1 of 4 on 10.2); with it, none in 11 runs on 10.2 to 12.1.
  - **Every register is read first,** as gdb writes back only those that differ from what it has read: where gdb can't write the extended registers (below), a call stopped at its first instruction, which hasn't changed them, is then popped without writing them (checked under the AMX shim, §6.5).
  - **One that can't be popped** keeps the program from running, as unrestored registers do (§3.6), with `kill` as the only way out. gdb 8.2 to 16 can't pop one stopped in an inlined function (§8.2).
  - **One whose frame gdb lost.** A Ctrl-C that quits gdb in the middle of popping a call (`pop_dummy_frame`) can leave gdb's record of the call, and its breakpoint, with the frame gone, so `pop_calls` can't find it (seen with typed Ctrl-Cs on gdb 10.2 to 17.1, plain gdb included). Ctrl-C is blocked before gdb pops a window's call (§3.4). And a window compares gdb's records (`maint print dummy-frames`) as it closes with those it had as its first call began: one left is reported, with its breakpoint's address, and keeps the program from running (`_Window._check_records`, `window_call_record_left`, simulated).
  - **`set backtrace limit`,** at which `Frame.older()` stops, as `bt` does, would hide the call's dummy frame (frame #1, with a limit of 1): realm-gdb's own walks of a stack (`_stack`) lift it while they run (`_AllFrames`, `window_abandoned_calls.refused_limit`, `.stopped_limit`).
  - **The breakpoint that stops a refused call is set as C++** (§3.1): under Modula-2 `break *ADDR` is a syntax error (`window_language.modula_2_refused`). A call whose breakpoint can't be set at all gets a warning that it ran.
  - **Only the window's own calls are popped:** one of the user's, stopped on the same thread before the window opened, is left. The window notes the dummy frames already there, which `==` tells apart by gdb's frame ID, and pops only newer ones (`_dummy_frames`, `window_pop_baseline`); counting them wouldn't do, as the parked thread's frames shown on the host never reach the host's own stack.
  - **On another thread:** a call the window refuses, made on a thread a command in the window selected (`thread apply 2 print f()`, with may-call-functions turned back on), is stopped and popped on that thread too, which would otherwise run the function from its first instruction once the program did (`other_dummies`, `window_refused_call_other_thread`).
  - realm-gdb warns that such calls were abandoned, counting them and naming the parked threads, and that the program may be inconsistent (a lock the function took, say). A call it refused itself gets a note instead, as nothing of it ran; so does one left at its function's first instruction, as gdb 8.2 leaves a call it couldn't start (under the AMX shim: `call_entries`).
- **Free stack.** Realm's user-thread stacks have **no guard page below them** (`UserThread::start_thread` mprotects the extra page above the stack top), so a call that overran the stack would write over whatever lies below, with no fault. In the test program the page below happened to be a neighbouring stack's guard, which is luck of layout.
  - So if less than `_CALL_HEADROOM` (64 KiB) of a parked thread's stack is free below its saved SP, calls are refused while it is shown (`window_low_headroom`). A note says so once for a selection, and in one line for all the threads of a `realm-thread apply all` or `thread apply all bt`; a refused call's own error says why, as for the other reasons, plain commands' too.
  - A command in the window can turn may-call-functions back on. `inferior_call_pre` can't refuse a call, and writing the SP there is undone: gdb has already worked out the call's SP. So a breakpoint at the function's first instruction stops the call before it runs (`_stop_at_entry`), and the window abandons it, as above, with a note that nothing of it ran (`window_refused_call_note`).
  - Only calls the window refuses are stopped so: with the user's own may-call-functions off, `with may-call-functions on -- print f()` in a window that allows calls makes the call, as elsewhere (`window_user_calls_off`). And the window works out whether it refuses calls even when the user has them off, so that such a call doesn't get past a refusal for AMX or a second UI.
  - On gdb 8, which can't refuse calls, such a thread isn't shown at all.
  - This doesn't make a large call safe on a nearly full stack. The real fix is a guard page at the bottom of each stack (§8.1).
- **The saved SP is checked first.** It must lie inside the user thread's own stack (`_parked_problem`, `window_bad_context`): a corrupt `UserThread` with a wild SP would otherwise send a call to an arbitrary address.
- **Extended registers gdb can't write.** gdb 13 and older can't write the x87, SSE and AVX registers where the kernel's XSAVE area is bigger than their buffer, as with AMX on (§6.5). A call changes those registers, so neither gdb nor the window could put them back afterwards: gdb gives up at the first x87 register, leaving those changed and `$orig_rax` too (gdb 12.1 under the shim: one call from a thread stopped in a futex wait, then `continue`, and the program died of SIGABRT), and the window would put back the rest (`window_unwritable_register`) but refuse to let the program run. So calls are refused in windows there (`_calls_unwritable`, `window_calls_unwritable`).
  - **The check.** The first window that would allow calls writes `$xmm15`'s low half, changed, and back (`_probe_extended`), and keeps the outcome for the process (`window_extended_check_once`). It can't wait for the first call: once gdb has started one, the only way to stop it is the breakpoint at its first instruction, and popping it needs those writes. It reads the register as C++ (§3.1), a check that couldn't read it is tried again by the next window, and none is made while may-write-registers is off, which says nothing of gdb's ability (`window_may_write_registers_off`). On aarch64 nothing is checked.
  - **What the user sees.** A note, once, quoting gdb's error, saying that gdb's own calls fail there too, and, for the kernel's "Couldn't write extended state status", that gdb 14 and later can write them. A refused call in `rt` or `realm-thread apply` gets gdb's "may-call-functions is off", with the reason added; a refused plain `print f()` gets gdb's message alone, and then, as its window closes, the reason, once for the selection. gdb 8 can't refuse calls: there the note warns against making any while a parked thread is shown.
- **A host a syscall catchpoint stopped.** A thread stopped at a system call's entry makes that system call when resumed, and a function call resumes it. On x86 Linux gdb cancels the system call (it writes `orig_rax` -1 with the call's pc), so the program sees it fail with ENOSYS: plain gdb 17.1's `print f()` at a `catch syscall clock_nanosleep` stop left `clock_nanosleep` returning -38. On aarch64 Linux and on FreeBSD the kernel makes it first, with the call's arguments: `realm_gdb_test_add(1, 2)` returned 2 on aarch64, and on FreeBSD the program exited, plain gdb's call included.
  - A window on such a thread refuses calls, saying why and to continue past it (`_at_syscall`, `window_syscall_stop`); on gdb 8 it doesn't show the parked thread there. gdb doesn't say whether the stop is at the entry or the return, so both count.
  - Linux marks such a stop in its siginfo (`si_code` SIGTRAP | 0x80, as gdb asks for `PTRACE_O_TRACESYSGOOD`). FreeBSD gives no siginfo there, so its stop events are noted (gdb ≥ 13, which gives Python catchpoints). `info program`, which would tell, made gdb 15.1 on FreeBSD fail an internal assertion (`stop_pc`) after a window's call had let other threads run.
- **A call that runs too long** is stopped and unwound: by gdb's own timeout (gdb ≥ 15), and by realm-gdb's (`_CallDeadline`), a Python thread that sends the call's thread a SIGINT, as a Ctrl-C would, after `_CALL_TIMEOUT` (10) seconds where gdb doesn't time calls out (before gdb 15, or where `show direct-call-timeout` says the target can't: FreeBSD's native target, which isn't asynchronous), and after 12 seconds elsewhere, as a backstop (FreeBSD's gdb 15.1 didn't stop calls in CI). A note says so (`window_call_timeout`). Only where gdb debugs the program natively and stops at a SIGINT without passing it on (`handle SIGINT stop nopass`, gdb's default); not to a thread that has already stopped (Linux's `/proc`), which would leave the SIGINT for later; and not while gdb holds Python's lock in a call, as gdb 8.2 does in one made from Python.

### 3.4 Nothing else may run meanwhile

**Nested event loops.** gdb's pager and its queries wait for input in a nested event loop, and there another UI (a second MI `new-ui`, say) can run commands, `-exec-continue` included. So inside a window:

- output is captured rather than paged;
- `confirm` is off, so queries take their default answer instead of waiting.

**Other UIs during a function call.** gdb blocks only the UI that makes a call while it runs (`run_inferior_call` sets that UI's `prompt_state` to blocked; `all_uis_on_sync_execution_starting` is called only for execution commands, and blocks only UIs waiting to be prompted). Another UI's input is served in the call's nested event loop, while the host has the parked thread's registers and the call uses the parked stack: MI's `-target-detach` then crashed gdb 16.3 and the attached program, `-exec-continue` of another thread ran it beside the call, and `-gdb-exit` killed the program, silently (9.2, 12.1 and 16.3). So:

- **calls are refused in windows while a second UI may be open** (`_calls_second_ui`), as where gdb can't write the extended registers: one seen by `hook-new-ui`, one named by `-ex new-ui` on gdb's command line, or (Linux) an extra terminal or named pipe gdb has open (`new-ui` takes a FIFO too; gdb's own pipes are unnamed), checked as each window opens, and named, with its file descriptor (`_other_terminal`, `other_terminal_fifo`). A note says why once per session, and a refused call's error gets the reason (`window_second_ui_calls`, `mi_new_ui.apply`). gdb 8, which can't refuse calls, warns instead;
- **a resume of another thread during a window's call** gets a warning (`_on_cont`): another UI's command, or a thread the function started, which gdb 14 and older let run.

A second UI that realm-gdb doesn't see (on FreeBSD; on something other than a terminal or a named pipe) is still a hazard during calls.

**Signals to gdb** (`_HeldSignals`):

- **SIGTERM and SIGHUP** are held until the window closes, then delivered; in `rt` and `realm-thread apply`, once what was collected, and the notes, are printed (`_let_held`; `window_signals`, `.TERM_output`). gdb acts on both by killing or detaching from the program and exiting, SIGTERM in the middle of a command, SIGHUP from a call's nested event loop.
  - gdb's handler is swapped for a Python one that only records the signal, and put back with libc's `sigaction()`; one that Python runs once the window has closed passes its signal on. Blocking isn't enough: from gdb 10 on, gdb's worker threads leave SIGTERM unblocked, and on gdb 10–11 one arriving there corrupted an attached program with the signal blocked on the main thread. Without ctypes, the signals are only blocked on the main thread, which before gdb 10 is gdb's only thread.
- **Other signals that would end gdb,** those it leaves at their default action, are held the same way while their action is the default: SIGUSR1, SIGUSR2, SIGALRM, SIGVTALRM, SIGPROF, SIGXCPU, SIGIO, SIGPWR, SIGSTKFLT (by number on Linux, as Python names it only from 3.11), SIGLOST, SIGEMT (FreeBSD), the real-time signals, and SIGPIPE and SIGXFSZ if gdb hasn't ignored them (it has, on Linux). Unheld, SIGUSR1 killed gdb in a window (`window_holds_fatal_signals`). **Ctrl-Z (SIGTSTP)** is held the same way, as gdb handles it only as it reads a line: it stops gdb once the window has closed.
  - **Not held:** SIGILL, SIGTRAP and SIGSYS, which gdb leaves at their default too, and SIGSEGV, SIGBUS, SIGFPE and SIGABRT, which gdb handles by reporting a fatal error and dying. A fault in gdb itself raises them, and a handler that only noted one would return to the fault, again and again. Sent to gdb during a window's call, each ends gdb, and an attached program died (9.2, 12.1 and 17.1; on 9.2 SIGFPE instead abandoned the call); on Linux gdb's death kills an attached program (§3.7). SIGQUIT is harmless: gdb's handler of it does nothing (`async_do_nothing`). SIGTTOU, SIGTTIN and SIGSTOP: §8.2.
- **Ctrl-C (SIGINT)** is blocked on gdb's main thread while a window is open (`_block_sigint`), but for what must be interruptible:
  - **the window's function calls,** unwound when interrupted: it is let through as each starts (as its `inferior_call_pre` ends) and blocked again as it ends (as its `inferior_call_post` begins);
  - **a plain command typed at a terminal,** which gdb runs itself (§3.9);
  - **on gdb ≥ 10, the command `rt` and `realm-thread apply` run** (`_interruptibly`): gdb quits it, and Python code it runs (a pretty-printer, `rt python`) gets the KeyboardInterrupt, as without a window, so a long `rt bt full` or a looping pretty-printer can be cut short (`window_interrupt_command`, `terminal.rt_ctrl_c_calls`). `realm-thread apply all` and the parked section of `thread apply all bt` then stop at the next parked thread, after printing what they collected, and the notes; the interrupted command's own output is lost.

  Once one of a command's calls has ended, Ctrl-C is held for the rest of it, but for its later calls, as gdb pops the call (below). One pressed while it is blocked is held until the window is closed and what the command left is printed, then quits what comes next (`hold_sigint`, `window_interrupt_held`); landing as the window closed, inside it, it would skip printing them, and one-time notes, marked as said, would never come again. `realm-thread apply all` also stops at the next parked thread after a call that a Ctrl-C interrupted (told by the call's `$_siginfo` as it ends) or stopped at its entry (below; `window_apply_call_interrupted`).
  - **Why it is blocked.** Unblocked, a Ctrl-C landing in a window's teardown (one every 7 ms, under a stress test) left the window's settings (`scheduler-locking on`, `confirm off`), Python's handlers on SIGTERM and SIGHUP, or a window marked closed but still current, after which `continue`, `kill`, `detach` and `quit` were refused for good. One landing just before `close` left the window for the next prompt, which MI lacks: an IDE's `-exec-continue` then ran the program with the parked registers, and it aborted. And on gdb 8.2 and 9.2 one landing while Python ran a command killed gdb (§8.2).
  - **Blocking, not a handler:** on gdb 8.2 and 9.2 Python's own SIGINT handler is what kills gdb, so it is blocked, by `pthread_sigmask`, on the main thread; gdb's worker threads (gdb ≥ 10) block it themselves. `window_holds_fatal_signals` checks `SigBlk` inside a window and after it.
  - **gdb 8.2 and 9.2** die when Ctrl-C lands while Python runs a command or a call made from Python (§8.2). There it is let through only for a call that a gdb command makes itself, with no Python beneath (`_python_beneath`: a plain `print f()` typed with a thread selected), not for typed plain commands, which may run Python (a pretty-printer), nor for `rt`'s command. That is told by a feature that came with gdb 10's fix, `Architecture.registers` (`_SIGINT_IN_PYTHON_SAFE`). A call that hangs there is stopped by realm-gdb's deadline (§3.3), but on 8.2 one made from Python, which only SIGKILL ends (`window_interrupted_call` skips on 8.2 and 9.2, once the program has carried on).
  - **A call within a call.** gdb makes calls of its own once the window's has begun, before it runs (`malloc`, for a string argument's copy). Only the end of the window's call blocks Ctrl-C, so that the call itself stays interruptible (`window_holds_fatal_signals`).
  - **A thread that doesn't block it** takes it instead: Linux gives a process's signal to its main thread, unless that blocks it, and then to another thread that doesn't. gdb's own threads block it, and so do gdb.Thread's and the `threading` threads started once realm-gdb has loaded, which block it as they start (`_install_thread_sigmask`, which wraps `Thread._bootstrap`; `window_interrupt_other_thread.default`). One started before, with `_thread`, or by a C extension, may not, and gdb's handler then runs there; gdb puts its handler back each time it runs Python or a command (`set_active_ext_lang`), so Ctrl-C can't be ignored instead. gdb 8.2 and 9.2 die of it as of one on the main thread (Ubuntu 20.04's 9.2, attached, in `realm-thread apply all bt full`: three times of three, and the program then died of Realm's assertions); gdb 17 and later die of an internal error (`ext_lang_guard`), told by `gdb.warning`, which came with it (`_SIGINT_MAIN_THREAD_ONLY`); gdb 10 to 16 quit wherever they are, and such a thread taking a SIGINT every 20–100 ms while windows made calls left a call's breakpoint in a parked thread's stack (§3.3) on 10.2, 12.1 and 16.3, and once a user's breakpoint disabled for good. So on every gdb, parked threads aren't shown while such a thread runs: realm-gdb says which (its LWP), why, and to block SIGINT in it (`_sigint_takers`, from each thread's `SigBlk` in `/proc`, on Linux; `window_interrupt_other_thread`).
  - **What gdb hands Python.** A quit that came while gdb ran is moved into Python as gdb next runs Python, and Python raises it before the first line of whatever runs then, which no `try` can catch. Blocking doesn't stop that one: it came while Ctrl-C was let through. Raised in realm-gdb's handler of a call's `inferior_call_pre`, a Ctrl-C typed at random in `print f(1)+f(2)+...` with a thread selected made a call run with none of what a window's call needs (it stopped at the user's breakpoint, the other threads ran, on 16.3), or left `scheduler-locking on` for good (14.2, at its `inferior_call_post`). So realm-gdb is Python's handler of SIGINT (`_on_python_sigint`, in front of Python's own; gdb's own stays the process's, put back with `sigaction()`): while a window is open, one that lands in realm-gdb's own code, told by its code objects, is held, blocked and raised again on gdb's main thread (`_hold_sigint`), and in its handler of `inferior_call` always. Elsewhere it raises KeyboardInterrupt, as Python's does, and so in the functions between `_interruptibly` and gdb (`_apply_execute`, `_execute`, `_cli_output`), to quit `rt`'s command (`terminal.plain_ctrl_c_calls`, 40 Ctrl-Cs at random; `window_quit_at_call`).
  - **Pressed before a call,** a Ctrl-C pending as a window's call is set up stops the call at its first instruction, as a refused call is, so that nothing of it runs, with a note (`_stop_at_entry(..., "interrupted")`, `window_ctrl_c_before_call`). Nothing is sent to the program: passed to a call that then failed before it ran (it couldn't write its argument), the SIGINT would be left for the program, which stopped with it, or died of it with `handle SIGINT pass` (`window_ctrl_c_before_call.failing`). If the call can't be stopped so (no breakpoint could be made), the Ctrl-C is held, to land once the window is closed, and the call runs (`window_ctrl_c_before_call.unstoppable`).
  - **Landing in realm-gdb's code while a call runs** (a posted closer, §3.9), it is passed to the call as gdb passes one, SIGINT to the program, which only the call's thread takes, so that gdb stops the call and unwinds it (`_pass_sigint_to_call`): only once the call is running (`_call_executing`), on Linux, which gives a process's signal only to a thread that runs, and where gdb runs the program natively (`_native_pid`). FreeBSD gave it to a thread gdb held, and the call ran on; a remote target's process ID is another machine's. Else it is held. It can't be handed to gdb instead: Python would raise it again at once, and `gdb.interrupt` on gdb's main thread hands it back to Python as it returns. A DAP `cancel` during a window's call interrupts the call.
  - **Popping.** gdb pops a call's frame once its `inferior_call_post` is over, and a Ctrl-C that quits gdb in the middle of that leaves the call's breakpoint in the parked thread's stack (§3.3); so that event blocks Ctrl-C, in every window. A call gdb makes as it sets up the window's (`malloc`) is popped with Ctrl-C let through, as the window's own call must be interruptible: §8.2.
  - **At an idle prompt,** a Ctrl-C held by a window closed there, or one gdb hands realm-gdb's prompt handler or prompt hook with no window open, says "Quit", as gdb does at its prompt, rather than a Python exception (`_let_held`, `prompt_hook_interrupted`).
  - **As a typed plain command's window lets Ctrl-C through,** one pending lands, and the command quits, its window closed on the way out (`terminal.plain_handoff_interrupted`).
  - **gdb 8** takes a KeyboardInterrupt out of a Python command for an error ("Python Exception <class 'KeyboardInterrupt'> Quit: Error occurred in Python command: Quit"): realm-gdb-guard, the hook, and realm-gdb's own commands (`_Gdb8Quit`) say "Quit" instead, as later gdbs do (`_COMMANDS_QUIT`, told by `Value.format_string`, which came with gdb 9's fix). One that lands before the hook's first line still shows gdb 8's message.
- **`gdb.events.gdb_exiting`** (gdb ≥ 12) closes a window that is still open.
- **gdb's internal problems.** With `confirm off`, gdb takes an internal error or warning's "Quit this debugging session?" as yes (`rt maint internal-warning X` at a terminal, attached, killed the program). In a window these settings are "no", so the problem ends the command, and the window closes on the way out (`window_internal_problem`). gdb 12 to 16 also die ("Recursive internal problem"), with or without realm-gdb, of the backtrace they print for an internal error in a command whose output is collected, as `rt`'s is: windows turn that backtrace off, and the command is aborted instead. (`realm-thread apply 3 maint internal-error X`, attached, killed gdb 12.1, 14.2 and 16.3, and the program, without it; with it gdb lived.)
- **Setting up and tearing down.** A Ctrl-C while a window swaps the signal handlers, or changes the settings, undoes what it had done (`window_setup_interrupted`). As it closes, reading and writing each setting, and enabling each breakpoint, are retried after a KeyboardInterrupt, and the settings are put back even if enabling the breakpoints fails.
- **Python's exit.** A `SystemExit` (`python sys.exit()`, a sourced script that ends with one) makes gdb 8.2–14 call `exit()` at once: no hook runs, and no `gdb_exiting`, and an attached program was left with the parked context, and died (12.1, 14.2). realm-gdb registers a Python exit handler that does as `gdb_exiting` does, which Python runs while gdb can still write registers (`window_python_exit`). gdb 15 reports the exception and carries on, and gdb 16 and later quit properly.

### 3.5 Checks on a parked thread (`_parked_problem`)

A parked thread isn't shown, and the output says why in its place (`<not shown: ...>`), when:

- it is running (`it is running on thread N`; `RUNNING  (on thread N)` in the list);
- some thread's SP is on its stack, so that thread is executing it while `ut->running` is still false (`it is switching contexts on thread N`): Realm sets and clears the flag around `swapcontext`, not atomically with it, so the saved context is then stale (`switching_user_thread`).
- it has never run: its PC is its entry point (`not started yet; will begin in F`; `not started` in the list);
- its state can't be read (`cannot read it: ...`);
- its saved SP lies outside its own stack.

### 3.6 Refusing commands

While a window is open, `realm-gdb-guard` refuses these, from a `hook-COMMAND` for each that the gdb in use has (`_install_hooks`; `refused_in_window`, 89 variants, and `refusal_messages`):

- `continue`, `signal`;
- `step`, `stepi`, `next`, `nexti`, `finish`, `until`, `advance`, `jump`, `return`, and the `reverse-*` commands;
- `detach`, `detach inferiors`, `disconnect`, `kill`, `kill inferiors`, `quit`;
- `run`, `start`, `starti`, `attach`, `core-file`, every `target` subcommand, and `load`; and `target record`, a deprecated command of its own that starts record-full, which `help target` and `complete` leave out, found with `help target record` (`_DEPRECATED_GUARDED`): unguarded, `realm-thread apply all target record` recorded the later windows' register writes, and replaying them crashed the program (13.2, 17.1) or gdb (18.1);
- `generate-core-file` (`gcore`): a core written then would hold the parked context in the host;
- `checkpoint` and `restart`;
- `record`, `record full` and `record btrace` (whose subcommands run through `target record-btrace`), and `record full restore`, which loads a core file as `core-file` does, killing the program without asking (it calls `core_file_command` itself, not through `target core`);
- `interpreter-exec`, which can run MI commands;
- `queue-signal`, which would give the signal to the host;
- `monitor` and `maintenance packet`, which on a remote target can do anything;
- the MI commands that would do the same, run by Python's `gdb.execute_mi` (`-exec-continue`, `-exec-step`, ..., `-target-detach`, `-target-download`, `-target-flash-erase`, `-trace-find`, `-gdb-exit`, `-interpreter-exec`, `-file-exec-and-symbols`, ...), which realm-gdb wraps (`_MI_GUARDED`, §3.9): a script sourced after a failed top-level command, whose window it can't be told from part of, would otherwise resume the program with the window open (`plain_failed_top_level`);
- `shell` (`!`), `make`, `pipe` (`|`) and `edit`, which start another program. `rt` and `realm-thread apply` run them without a window (§3.8), but a command that has one would run them with the host holding the parked registers: `rt eval "shell ..."`, a user-defined command run with `rt`, Python's `gdb.execute` in `rt python` (`external_nested_refused`). A plain command's window is closed by the next hooked command it runs (§3.9), so plain `eval "shell ..."` runs the shell without one.

Other details:

- **Aliases and nesting.** Aliases (`c`, `s`, `fin`, `gcore`, ...) and nested commands (`frame apply 1 return`, Python's `gdb.execute('continue')`) hit the same hooks.
- **Outside windows the hooks do nothing,** but where a host's registers could not be put back: then these commands, but `kill` and `queue-signal`, are refused until `realm-thread back` succeeds or the program is killed (`window_unrestored`). That was seen only on CI runners where gdb 12 could write no extended registers (§6.5), and calls are refused where they would cause it (§3.3), so it is reached only on gdb 8, which can't refuse calls, or through a failure not yet seen.
  - **The messages name what is left, and why:** the registers (at most six, in order, and how many more) and gdb's error writing them, for example "thread 5's own registers ($xmm0, $xmm1: Couldn't write extended state status: Bad address)". `realm-thread back` tries again, and warns while it still can't (`window_unwritable_register`).
  - **Function calls are refused meanwhile:** realm-gdb turns may-call-functions off, saying so after the window's warnings, and on again once the registers are back (saying so) or the program is gone, unless it was changed meanwhile (`_unrestored_calls`): a call lets the program run, the host perhaps on the parked thread's stack, with breakpoints live (`window_close_fails`). gdb 8 gets a warning instead. `delete checkpoint`, `info static-tracepoint-markers` and `strace`, refused in windows (below), are refused then too (`_RUNS_PROGRAM`).
  - **With a parked thread selected,** `realm-thread back` only tries again, and says the selection is kept, as realm-gdb's own register writes run no hooks (§3.1, `window_unrestored_selected`). `realm-thread N` on such a thread is refused at once.
  - **A function call that couldn't be popped** (§3.3) is listed the same way, with only `kill` offered: its dummy frame is in the parked thread's stack, which the host no longer shows.
  - **No second window on such a thread** (`_check_unrestored`, `window_unrestored_host`): it would save the parked thread's registers as the host's own, and a retry would then write the first window's leftovers back and let the program run.
  - **`quit` from a script.** At a terminal, `quit` is refused while an attached program is left so, as the message offers `kill`; a program gdb started is killed by `quit` anyway, so then `quit` goes ahead. From a file or a pipe, gdb runs `quit` at every end of its input, and refusing it would loop for good (1,234 refusals in 20 seconds on 17.1). So there, in batch mode from a terminal too, and on gdb ≥ 12 wherever gdb exits anyway (the end of `-batch`, `-gdb-exit`: `gdb_exiting`), realm-gdb kills each attached program still left, saying why (`_kill_unrestored`, `window_unrestored_quit`). Before gdb 12 there is no event at those exits, and gdb detaches from the program (9.2, 11.2).
    - **SIGTERM on gdb 12 and 13:** the quit it makes raises KeyboardInterrupt as the first `gdb_exiting` handler starts (§2.3), so the handler is connected twice; gdb carries on to the second, which does nothing when the first has run (`window_unrestored_signal`).
    - **FreeBSD:** gdb 15.1's kill of a program it attached to, and hasn't let run since, lets the program run on unkilled, and waits for it to end (§8.9). So realm-gdb's own kill sends the program SIGKILL every 5 ms until gdb's is over (`_KillNudge`, FreeBSD's native target only): one sent while it is stopped is lost, but the first after gdb lets it run ends it.
  - **`may-write-registers off`,** turned off by a command in the window (gdb ≥ 14 allows it with a live process), is turned on to put the registers back, and off again (`window_may_write_registers`).
  - **A resume that runs no hook** while registers are left (MI's own `-exec-continue`) has the host stopped before it runs (§3.7, `window_bypass_stopped.unrestored`).
- **A check that fails refuses.** If realm-gdb's own check of a command raises an unexpected error (a bug, or windows of mixed versions, §8.7), a command that may have to be refused (guarded, external or acting) is refused, saying so and that `REALM_GDB_DEBUG=1` shows where, while a window is open, registers are left, or a thread is selected; elsewhere it runs (`window_guard_error`). A window whose `close` raises unexpectedly (not Ctrl-C, which leaves it open for the next prompt) is kept as one whose registers couldn't be put back (`_fail_closed`, `window_close_fails`).
- **`with SETTING VALUE -- COMMAND`** sets the setting without `set`, so without its hook. In `rt` and `realm-thread apply`, whose text realm-gdb reads, a `with` of a setting whose `set` is refused in a window (below), or of `logging enabled` (§3.8), is refused as `set` of it is, however it comes there (abbreviated, in a literal `eval`, wrapped in `frame apply`: `_with_refused`, `refused_in_window.with_architecture` and the like), naming the thread that would show the parked one. gdb 9 to 11 don't put the architecture, endian or osabi back after `with` ("Requires an argument"): `realm-thread apply PTR with architecture i386:x64-32 -- print $pc` left the host's registers unrestored, and in a batch the attached program died of SIGILL. A user-defined command, or an `eval` with arguments to format, that runs such a `with` isn't seen.
  - **Around a command that opens a window** (`with architecture X -- bt`, with a parked thread selected, or around `rt` or `realm-thread apply`), `with` runs first, so the window would open with the setting changed, and put back what it found. hook-with notes the settings that matter there (`_WITH_GUARDED`: `architecture`, `endian`, `osabi`, `tdesc filename`, `host-charset`) as the outermost `with` begins, and hookpost-with forgets them; after a `with` that failed, which runs no hookpost, the prompt does, or from gdb 15 gdb's event loop, and a `set` of one drops it, as the user's own doing. (Before gdb 12, `gdb.parameter` has "" for `endian`, `osabi` and `architecture` until they are set, then "auto": both count as "auto".) While one differs, no window opens, nor is the program read for one: "can't show a parked Realm user thread on thread 5 inside 'with architecture': it would change which registers that thread has, ..." (`with_guarded_around`).
- **Refused in a window only** (`_WINDOW_GUARDED`), each with its own reason in the refusal; hooked, they also close a failed plain command's window first:
  - `new-ui`, whose UI gdb runs commands from even during a call (§3.4);
  - `maint dump-me`, which aborts gdb (with `confirm off` it doesn't ask);
  - `file`, `exec-file`, `symbol-file`, `add-symbol-file`, `add-symbol-file-from-memory`, `remove-symbol-file` and `nosharedlibrary`, which replace, add or drop the program's file or symbols without asking there (`realm-thread apply PTR symbol-file` dropped every symbol, and no user thread could be found afterwards), `set sysroot` and `set solib-search-path`, which can drop librealm's, and MI's `-file-exec-and-symbols`, `-file-exec-file` and `-file-symbol-file`;
  - `delete checkpoint`, which may make a function call (`waitpid`) on the host;
  - `info static-tracepoint-markers` and `strace` (whose `-m` asks for markers), with which gdb lets the whole program run while it asks the in-process agent (the program then aborted); `strace` doesn't count as showing a selection either;
  - `set endian`, `set tdesc filename` (and `unset`), `set architecture` (`set processor`) and `set osabi`, which change how gdb reads the host's registers, which it has, or their sizes: after `realm-thread apply PTR set architecture i386:x64-32` the window couldn't put `$rbp`, `$rsp` and `$rip` back ("Invalid cast"), and in a batch the attached program was killed at the end (only `set architecture auto` gets the gdbarch back);
  - `set host-charset` and `set charset`: Python's strings, realm-gdb's own commands among them, are passed to gdb in the host charset, so that after `set host-charset EBCDIC-US` none could put the host's registers back ("Could not convert arguments to Python string"), nor kill the program as gdb let go of it (11.2, 16.3, 17.1);
  - `tfind` and its subcommands, and MI's `-trace-find`, which would have gdb read a trace frame's registers instead of the host's;
  - `flash-erase`, as `load`;
  - `info threads`, which would list the host at the parked thread's frame (as `rt realm-thread` would, refused for that reason, §3.8);
  - and Python's `_gdb.execute_mi`, the C module's function that `gdb.execute_mi` comes from, is wrapped too.
- **The user's own hooks,** defined before realm-gdb loads (in `~/.gdbinit`, say), are kept: realm-gdb defines the hook as its check followed by the user's commands, read from `show user`, and says so at load ("your hook-quit now runs realm-gdb's check of 'quit' first"), once, however often it loads (`user_hook_kept`). Left without its check, a `define hook-quit` that only sets `confirm off`, a common idiom, would keep a failed plain command's window open through `quit`, and an attached program then died on gdb 11.
  - **In hook-CMD of a command that shows a selection, the check comes last** ("... runs realm-gdb's check of 'print' after its own commands"): a hooked command among the user's lines (`output 0` in a `hook-print`) would close the window the check opened, and `print` would run on the host. Elsewhere it stays first: a guard must refuse before the user's lines run, and in hookpost-CMD it closes the window before them.
  - **A hook the user defines after realm-gdb has loaded** (typed, or in a sourced file) would replace realm-gdb's, and with it the command's check: `hookpost-define` puts realm-gdb's check back in front of it, saying so (`user_hook_after_load`).
  - **A `define hook-CMD` that runs no hooks** (in a block, `if 1` ... `end`, in a user-defined command, in breakpoint commands; or from Python with its body) replaces realm-gdb's hook unseen. Each window checks, with one `show user` (about 3 ms with some 300 hooks), that every hook of realm-gdb's still has its check, and puts it back with the user's lines if not, saying so; so do each `define` and each prompt while registers are left that couldn't be put back (`_check_guard_hooks`, `user_hook_after_load`). One defined inside a window, by a command run there, gets past that window's guard (§8.2). Lines of an older realm-gdb.py's check (`realm-thread-guard`, its earlier name) are dropped, not kept as the user's (`old_guard_dropped`).
- **An interrupted load.** Until realm-gdb has installed its hooks, the commands it must guard (`continue`, `step`, `next`, `finish`, `detach`, `kill`, `quit`, `run`) count as unguarded, so a Ctrl-C while librealm loads (during `attach`, say) leaves windows refused, with the reason and a note that loading was interrupted; loading it again finishes (`load_interrupted`). The hooks are counted only once they are all defined, and a load keeps the earlier load's record of its hooks (`_hooked`, `_unguarded`), whose hooks, the same, are in place meanwhile: a load interrupted during a window's call (one that loads a library with a copy embedded) mustn't leave that window's guards refusing nothing.
  - **`q` at gdb's pager during the banner,** which gdb's own messages can bring up as it attaches (`gdb -p PID`), isn't an interrupted load: everything is in place by then. The banner is two lines, which leave room on a 24-line terminal for gdb's messages (`terminal.banner_pager`), and isn't printed in batch mode; `realm-help` prints the full summary.
  - **What to load again:** the note, and the reason windows don't open, say to `source` realm-gdb.py from Realm's `src/realm`. librealm's embedded copy isn't run again by gdb, even when `sharedlibrary` reads librealm again.
- **A command realm-gdb runs for itself** (`_internal`: its register writes, the `return` that pops a call) runs no checks of its own; any other guarded command that runs meanwhile is checked (§3.1).
- **Nested windows.** `realm-thread apply` and `thread apply all bt` can't run inside a window. Other `thread apply` and `frame apply` commands can.
- **One hook command for everything.** The same `realm-gdb-guard` hooks also show a selected parked thread to plain commands, and refuse others while one is selected (§3.9); `hookpost-COMMAND` runs `realm-gdb-guard --after COMMAND`. Its name leaves `realm-th` an abbreviation of `realm-thread`. It is deprecated itself, which keeps it out of completion (`realm-<TAB>`, `rt <TAB>`), and run once at load with no argument, which does nothing, to use up gdb's one-time warning (`_hide_guard`).
- **Out of sight.** Each hook that holds only realm-gdb's check is deprecated (`maintenance deprecate`), which keeps it out of completion and `help` (else `info h<TAB>` would list some 50 `info hook-*` entries, and `help user-defined` some 340 hooks). gdb runs a hook through the command's hook pointer, not by its name, so no deprecation warning comes. A hook with lines of the user's isn't deprecated, and `apropos` still lists them all (`loaded`).
  - **Abbreviations.** The hooks are in the same lists as the commands they hook, so an abbreviation that gdb took for one subcommand (`info h` for `info handle`, `set ho` for `set host-charset`, `tui window h`) would be ambiguous with them. realm-gdb makes each such abbreviation an alias of its subcommand (`alias -a`, which gdb takes over the hooks: `_keep_abbreviations`, `loaded`); gdb ≥ 10's `help` then lists it among the command's names. One that only a hook's name completes stays as it is (§8.7).
- **Finding commands.** `_existing_commands` asks `complete NAME`; `_subcommands` and `_subcommand_names` read `help PREFIX`, only for a prefix that exists; a deprecated command is found with `help NAME`. So nothing that fails runs while librealm loads, where it matters twice: gdb 10 and 12 return from `run` before the program stops after a command that fails there (`help memory-tag`, before gdb 11, broke every live test on 10.2); and gdb 12 stops a function call during which a `new_objfile` handler runs a command that fails, even one Python catches ("stopped while in a function called from GDB", checked without realm-gdb), as when a window's call loads a library with an embedded copy (`window_reload_in_call`). So the aliases above aren't made again as the script loads again (`_abbreviations`), and subcommand names come from `help PREFIX`, not `complete`, which lists the program's symbols after `set`.
  - `help PREFIX` lists user-defined commands too, realm-gdb's own hooks among them: each load would hook the hooks of the one before (`append binary hook-hook-memory`), doubling their number, and the eighth took 90 seconds; every re-read of librealm's symbols (`file PROG`, a rebuilt program run again) loads the script again. Hooks and other user-defined commands are left out (`load_repeated`).
  - The window settings' `set` commands are looked up as settings: `complete set X` completes an expression too once there are symbols (`set unwind-on-signal`, which gdb 14 and older lack, would be found as `set signal`). `complete` lists nothing with `set max-completions 0`, so completions are unlimited while it asks (`max_completions_zero`).
  - Should realm-gdb fail to guard any of `continue`, `step`, `next`, `finish`, `detach`, `kill`, `quit` and `run`, which every gdb has, windows don't open at all, and `realm-thread` says why (§3.10). A user's own hook on one counts as a guard.
  - **gdb 18 under MI** returns some of `gdb.execute(..., to_string=True)`'s output as MI stream records (`~"continue\n"`), line by line. Every captured output goes through `_execute`, which decodes them, `_internal`'s too: else no command would be found, `rt`'s output would be garbled, and the target stack would read as no native target (§3.7).

### 3.7 What can't be covered

- **gdb dying with a window open** (kill -9, a crash, an internal error that quits) would leave an attached program running the parked context on the host, and so corrupt it. This is the one risk the unwinder approach doesn't have.
  - A program that gdb started dies with gdb, because gdb sets `PTRACE_O_EXITKILL`.
  - On Linux, with gdb running the program natively, a window sets that option on an attached program's host too, while it holds a parked thread's registers, and takes it off again once they are back (`_ExitKill`): gdb's death then kills the attached program rather than leave it to run on corrupted (`terminal.attach_gdb_killed` kills gdb in a window, in a console and under MI, and after one, when the program finishes cleanly). Linux can't read a thread's ptrace options, so the window sets gdb's own for an attached program (TRACESYSGOOD, TRACEFORK, TRACEVFORK, TRACECLONE, TRACEEXEC, TRACEVFORKDONE, the same on gdb 8.2 to 18.1) with EXITKILL added, and back without it, on the host and on any thread a call made meanwhile; it sets it again as each call stops, since gdb sets an attached thread's options at the first stop it sees of it.
  - The native target is told from gdb's target stack (`_native_pid`), decoded as all captured output is (§3.6): read raw under MI on gdb 18.1 it showed none, the option was never set, and the attached program aborted after gdb was killed in a window, 3 times of 3. (Not from `Inferior.connection`, which gdb 12 to 14 die of as they exit: `connpy_connection_dealloc`.)
  - A window whose host was running as it closed (below) can't take the option off, so gdb's death then kills the program. Not covered: Python without ctypes, remote targets, and FreeBSD with `kern.kill_on_debugger_exit` at 0; §8.1 has a Realm-side check that would cover them.
- **On FreeBSD** gdb dying kills an attached program instead: with `kern.kill_on_debugger_exit`, 1 by default, the kernel kills a traced process when its debugger exits. Checked on FreeBSD 15.1 with a program that attaches and exits without detaching: the target was killed with SIGKILL, and survived with the sysctl set to 0.
- **Other programs started in a window.** gdb's commands that start one (`shell`, `make`, `pipe`, `edit`) don't keep a window open while it runs (§3.8), and are refused inside a command that has one (§3.6); plain `pipe`, whose COMMAND would, is refused while a parked thread is selected (§3.9). Python code in a window that starts one (`rt python os.system(...)`, `subprocess`, an extension's command, a pretty-printer) is refused too, from Python's audit events (Python ≥ 3.8: `os.system`, `subprocess.Popen`, `os.exec*`, `os.posix_spawn`, `os.spawn*`, `os.fork`, `os.forkpty`, `pty.spawn`) and from `_posixsubprocess.fork_exec`, which multiprocessing starts programs with, raising no event, and which realm-gdb wraps; however it got the function, but on another thread of Python's (`_audit`, `external_nested_refused`). After a plain command that failed, its window is closed first, as by a hooked command, and the program runs. One started by other means (ctypes) still keeps the window open.
- **A resume that gets past the refusals.** Registers can't be put back from `gdb.events.cont` (§2.3): tried, it made gdb 12.1 segfault (the regcache freed under `proceed`) and gdb 16.3 fail an assertion (`pc_in_thread_step_range`). But `cont` comes from gdb's `proceed()` before it resumes anything, and not for function calls. So there, for a host with a parked thread's registers (a window's, or one left unrestored, §3.6), realm-gdb sends the host alone a SIGINT of its own (`_stop_before_run`: Linux's `tgkill`, FreeBSD's `thr_kill2`). A traced thread with a signal pending stops before it returns to user space, so the host runs no instruction, and gdb reports a SIGINT stop. The window, closing, checks the host's `$_siginfo` (SIGINT, `SI_TKILL` on Linux or `SI_LWP` on FreeBSD, from gdb's own process: `_our_sigint`), says the host stopped before it ran, and puts the registers back as usual. A host resumed in the background (`continue &`) may still be running as the window closes: it is kept with the unrestored, refused as they are, and put back once it has stopped, at the next prompt, guarded command or `realm-thread back` (`_retry_unrestored`). Where only other threads were resumed, the host's registers are put back as usual, with a warning. (`window_bypass_stopped.apply`, `.background`, `.unrestored`: a `continue` past a `define hook-continue` in a block, which no hook saw.)
  - Only where gdb debugs the program natively, stops at a SIGINT without passing it on (`handle SIGINT stop nopass`, gdb's default), and Python has ctypes. Elsewhere, or if the host didn't stop at that SIGINT, realm-gdb warns that the program may crash, and gives up on putting the registers back.
  - Costs (§8.2): the other threads run briefly, until gdb stops them; the host may stop at its breakpoint again; a signal gdb passes to the host as it resumes it is lost.
  - **References taken before realm-gdb loaded** to the functions it wraps (`from gdb import execute_mi`, in a module or in gdb's `python`, and closures over one) are pointed at the wrapper (`_rebind`, from the garbage collector's referrers: module dictionaries, `__main__`'s included, and closure cells), so that they are refused too (`execute_mi_taken_early`). Not those in a running function's variables, an object's attributes, a class's dictionary (Python caches those) or a `functools.partial`: those meet the SIGINT.
  - Nothing sees what resumes the program without gdb's `proceed()` (ptrace through ctypes), a remote target's packets (`RemoteTargetConnection.send_packet`, gdb ≥ 13), or a detach by such a path: no gdb gives Python a pre-detach event.
- **Commands that read their own input inside a window,** in a user-defined command run by `rt`, or a pretty-printer's `gdb.execute`, would run a nested input loop that `confirm off` doesn't avoid (before gdb 13; from 13 on, `gdb.execute` takes the body from its own text). Another UI could run a command meanwhile. `rt` and `realm-thread apply` refuse them themselves (§3.8).
- **gdb's own hazards with calls are unchanged.** For example, gdb 9.2 aborts on Ctrl-C during a pretty-printer's call in `bt full` even without realm-gdb, and the attached program then dies. And a Ctrl-C typed just as a call's thread stops, before gdb takes the terminal back from the program (in `call_thread_fsm::should_stop`, before any of realm-gdb's handlers run), goes to the program: gdb stops it at that SIGINT (`SI_KERNEL`, from the terminal) as it next resumes it, the next call or `continue`, with or without realm-gdb (seen in 3 of 24 runs of `terminal.rt_ctrl_c_calls`' 40 Ctrl-Cs, which continue past it once, if it isn't realm-gdb's own: `_our_sigint`).

### 3.8 Selecting a parked thread (`realm-thread N`, `rt`)

gdb gives Python no way to see or rewrite a command before it runs:

- the Python events are `stop`, `cont`, `before_prompt`, `inferior_call` and the like, with none before a command;
- gdb runs a `hook-COMMAND` without the command's arguments;
- replacing a built-in such as `backtrace` or `frame` from Python deletes gdb's own command.

So plain `bt` can't be redirected to a parked thread in a live process. It can, though, be given a window for its whole duration, by hooks that need no arguments (§3.9). A selection is remembered in Python (`_selections`), and both plain commands and a short prefix run commands on it:

- **`realm-thread N`** records the parked thread: its inferior, process, pointer, saved context, and frame 0 as the selected frame. Nothing in the program changes. The first selection explains what plain commands then do; later ones say it in one line. It then prints the selected thread's frame #0, as `thread N` does. Selecting the selected thread again starts it over at frame #0, rather than selecting it twice. `realm-thread back` prints the frame it is back at, the parked thread's or the thread's own, which also moves gdb's source position there for `list` (`terminal.repeat`).
- **Numbers.** `realm-thread` numbers the user threads, as `info threads` numbers gdb's, in the order they were made (the registry's, newest first, reversed) as it first lists or looks them up, and doesn't give a number again in that process (`_numbered`). The list has a header, a `*` on the selected one, and the states `parked`, `parked (selected)`, `parked (selected earlier)`, `not started` and `RUNNING`. Messages and headers name a user thread "user thread N (0x...)", as gdb names "thread N (Thread 0x... (LWP n))", and the prompt shows its number. A number given to no user thread (below 65536, where no user thread is) is refused, saying so; a value below 65536 from an expression (`realm-thread $n`) is taken as a number, as by `thread $n`; and where the registry can't be read, a lookup by number says why (`realm_thread_numbers`).
- **`realm-thread apply`** takes what `thread apply` takes: numbers, ranges `N-M`, pointers, `$n` and expressions in parentheses (the first word may be any expression; later ones must be numbers, ranges, pointers, `$n` or in parentheses, and the command begins at the first that isn't), each shown under a "User thread N (0x...):" header, one that can't be shown saying why in its place; an inverted range is refused, and one target alone gets no header. `apply`, `back` and `restore` are subcommands of the prefix command `realm-thread`, which gdb abbreviates (`realm-thread ap`), completes and has `help` for (`realm_thread_apply_lists`).
- **`rt COMMAND`** runs `COMMAND` in a register window, as `realm-thread apply N COMMAND` does, with the remembered frame selected first, and records the frame `COMMAND` left selected. So `rt frame 3` then `rt print VAR`, or `rt up` then `rt info locals`, behave as on a running thread. The host is whichever thread is selected when `rt` runs.
- **Frame motion is done by realm-gdb.** On every gdb from 8.2 to 17.1, `frame N`, `up` and `down` print the newly selected frame from gdb's selection-changed notification, which goes straight to the console rather than the collected output (§3.4), and under MI becomes a `=thread-selected` notification naming a parked frame. So inside a window realm-gdb handles `frame N`, `frame level N`, `up [N]` and `down [N]` itself, with gdb's aliases, counts and error messages (`_frame_motion`): it selects the frame from Python, which doesn't notify, then prints it with a plain `frame`. `frame function NAME`, `frame address ADDR` and `frame view ...` are selected with `select-frame`, which prints nothing, where it takes them (gdb ≥ 9, `_select_frame_forms`); before that they run as gdb's own (§8.5).
- **Checks before each `rt`** (`_check_selection`): the user thread must still be in the registry and parked, with the saved context it had when selected; otherwise the selection is dropped and `rt` says why (`select_stale`).
- **When the program runs** (`gdb.events.cont`, outside function calls and windows), the selected inferior's selections are dropped, or every inferior's with `schedule-multiple`, with a message: Realm may resume a parked thread meanwhile, and that can't be checked from the event. A program that exits, or is detached from, drops its selections silently. A function call made outside `rt` that lets other threads run leaves the selection, to be checked at the next `rt` (`select_dropped_when_running`).
- **The prompt** shows the current selection, as `[realm-thread N] (gdb)` (`_realm_prompt`; `select_prompt`, `select_prompt_setting`, `terminal.prompt`). It wraps whatever `gdb.prompt_hook` the user had, and puts that back when the last selection goes; a hook the user sets meanwhile is left alone. gdb makes whatever a prompt hook returns its `prompt` setting, so the hook strips its own earlier reminder before adding one, and once nothing is selected realm-gdb sets the prompt back without it, escaped so that `set prompt` keeps spaces at either end.
- **`thread apply`'s flags.** In `realm-thread apply` and the parked section of `thread apply all bt`, -q leaves out the "User thread N (0x...):" lines, -s the threads where the command fails or prints nothing, and -c goes on past a failure without failing at the end; without -c or -s, `realm-thread apply` goes on too, then fails with the first error, where `thread apply` stops. After `all`, and in `thread apply all bt`, `-ascending` goes from the oldest. An unknown flag is refused as gdb refuses one ("Unrecognized option at: -x ..."). So `realm-thread apply all -s frame apply all -s print VAR` shows just the frames that have VAR (`realm_thread_apply_flags`, `thread_apply_all_bt_forms.q_bt`). gdb 8.2's `thread apply` has no flags, and there `thread apply all -q bt` fails as gdb 8.2's own does.
- **As typed.** A backtrace run by `rt`, `realm-thread apply` or the parked section, from a command typed at the terminal, says "(More stack frames follow...)" when it stops short, as gdb's own does (from_tty; nothing else of a backtrace's depends on it). From gdb 17, whose `gdb.execute` can keep styling, their output is styled; `rt pipe`'s SHELL gets it unstyled, as gdb's pipe gives it (`terminal.output`).
- **Commands that start another program** run without a window, in `rt` and `realm-thread apply` (`_external`, `_apply_external`); otherwise the host would hold the parked registers, with SIGTERM and SIGHUP held, for as long as the other program ran (`select_external`, which reads the host's SP and PC from `/proc` meanwhile; `core_external`).
  - **`shell` (`!`) and `make`** look at nothing of the program's: gdb hands their text to the shell untouched.
  - **`edit`, bare or with a function or line,** uses gdb's current source position, which a parked frame's printing (`rt frame`, say) sets, not the registers (the same result, checked against gdb 9.2 and 18.1).
  - **`edit *EXPR`** evaluates EXPR in the selected frame: realm-gdb works out the location with `gdb.decode_line` in the window, then, with the window closed, prints gdb's "ADDR is in FUNC (FILE:LINE)." and runs `$EDITOR +LINE "FILE"`, as gdb's `edit_command` does.
  - **`pipe COMMAND | SHELL`** (and `|`, `-d DELIM`, gdb ≥ 9) runs COMMAND in the window, its output collected, then SHELL on that output with the window closed, setting `$_shell_exitcode` or `$_shell_exitsignal` (Ctrl-C during SHELL sets the latter, as with gdb's own). SHELL starts once COMMAND is done, rather than reading as it runs. With no COMMAND, gdb's would repeat the last command; `rt` refuses instead. `pipe` around a command that itself starts a program (`rt pipe shell ... | ...`) needs no window either.
  - **`realm-thread apply all`** runs these once for each parked thread, under its header.
- **Commands that read the terminal are refused inside `rt` and `realm-thread apply`** (`_NoTerminalInput`, `terminal_input_refused`), in windows and core-file views alike: the output is collected until the command is over, so the question wouldn't show, and in a window the host would hold the parked registers while waiting. Python's `input()` and `sys.stdin` raise an error that says why (`explore` asks its questions through them). Python's REPL (`pi`, which reads the terminal from C) is refused in windows by a `hook-python-interactive` guard; `rt pi EXPR` runs, as `python-interactive` reads the terminal only without an expression.
- **Commands that read the lines after them** (`commands`, `define`, `document`, `while`, `if`, `while-stepping`, `actions`, and `python`, `guile` and `compile code` given no code) are refused by `rt` and `realm-thread apply`, which can't pass those lines on (`_check_command`, `window_body_commands`). gdb ≥ 13 takes them from the command's own text when Python runs it, so there are none: `rt define foo` would empty `foo`, `rt commands 2` erase breakpoint 2's commands, and the lines the user typed next run as commands of their own; older gdbs would read them from the terminal, with the window open. The command is recognized whatever its abbreviation or alias (`py`, `comm`, an `alias` of the user's), by comparing gdb's `help` for it with each such command's (`_command_named`).
  - **`compile` and its alias `expression`** read lines whenever no code is left after their subcommand, options and format (`compile code -raw`, `compile print /x`, `expression print`); `compile file FILE` doesn't.
  - **At a terminal, the lines typed after one are read first:** else, refused, the command would leave them to run as gdb commands, and a Python block's `continue` would resume the program (`terminal.body_lines`). `rt` and `realm-thread apply` read them with Python's input(), up to their `end` (counting nested blocks), before anything else can fail, saying first that they will be dropped. From a pipe they aren't read, as input() would read through a buffer of Python's own, taking later commands with it; the lines then still run as commands (§8.5). In a script or a user-defined command, the failure ends it, and the lines with it.
  - **However they come:** `rt with confirm off -- define foo`, `rt eval "commands 2"`, `rt eval "if 1"` and the like are refused too, by hooks on `commands`, `define`, `document`, `while-stepping`, `actions`, `while` and `if` that refuse in a window whose output is collected (`_BODY_HOOKED`). A user-defined command run by `rt` that contains one is fine: its body is stored with it. So is a script run by `rt source FILE`, whose file gives its blocks' lines: `source` marks the window while it runs (`window_source_blocks`). A `source` that fails leaves the mark, as gdb runs no hookpost then, so the rest of that window's command (Python that catches the error) isn't refused these, and one would wait for lines.
  - **Bare `python`, `guile` and `compile code`, and `watch` without `-l`,** whose arguments a hook doesn't see, are refused only when `rt`'s own text names them: directly, after `with SETTING --`, in a literal `eval "TEXT"`, or after the commands that run others (`frame apply`, `thread apply`, `faas`, `taas`, `tfaas`, past their frames, threads and options: `_applied_command`), as `rt faas python` would read a body per frame, swallowing the commands typed after it. An alias of those (`alias fa = frame apply all`) is unwrapped by its expansion or, before gdb 10, its `help`. An `eval` with arguments to format can't be told (§8.2).
  - **An alias's default arguments** (`alias u2 = up 2`, gdb ≥ 10) are read from its `help` and put first, as gdb does, for `frame`, `up`, `down` and `pipe` (`_alias_expansion`, `window_alias_arguments`). Not for a command that reads a block: gdb drops an alias's arguments where it reads the block itself, as from `gdb.execute`, so `rt pyx`, with `alias pyx = python print(1)`, reads a body and is refused.
  - In a core file `rt` refuses them too: run with `gdb.execute` they would have no lines either (`core_body_commands`).
- **Commands that switch gdb's output** to a log file or the TUI's windows, or back, are refused in `rt` and `realm-thread apply`, core files' included, however they come there (`_STREAM_COMMANDS`, hooked, and `_collecting`; `refused_in_window`, `stream_refused_core`): `set logging enabled` (`set logging on` and `off`, separate commands before gdb 12), `set logging redirect` and `debugredirect`, `tui enable`, `tui disable`, and every TUI command that turns the TUI on first (`layout` and its subcommands, `focus`, `refresh`, `winheight`, `winwidth`, `tui reg`, `tabset`; from gdb 13 hooked by their `tui ...` names, as hooks on aliases never run). The TUI's `+`, `-`, `<` and `>` can't be hooked, so they are refused only when `rt`'s own text is one. gdb collects these commands' output in a stream of its own, keeps the stream it switches from to switch back to later, and crashes then, the collecting stream gone: `rt set logging enabled on` then a plain `set logging enabled off` was a SIGSEGV on gdb 13.2 to 17.1 (18.1 fixed logging's, not the TUI's). A layout made later (`tui new-layout`) isn't hooked.
  - **`with logging enabled VALUE -- COMMAND`** switches logging itself, and runs no `set` hook: it is refused when `rt`'s own text names it, unwrapped as bare `python` is (`_with_refused`, `window_logging_with`), as `rt with logging enabled off -- print 1`, logging on, crashed gdb 13.2 to 17.1 as the output was printed. Turning logging off around the collected command instead won't do: switching it inside a command whose output Python collects is what crashes, plain gdb too.
- **gdb's pager** stops the collected output once the window is closed. Ctrl-C works there, but on gdb 8.2 and 9.2 (§3.4), and is held if one came while the window was open, as it would lose the notes, landing first. `q` and Ctrl-C there cut the output short, and the notes and warnings come all the same (`terminal.pager_notes`).
- **`$_shell(...)`** (gdb ≥ 14) starts a shell command from an expression, which no hook sees: `rt` and `realm-thread apply` refuse command text that calls it literally. A user-defined command, an `eval`, or a convenience variable holding it (`set $f = $_shell`) still runs it with the window open, and so does a plain `print $_shell("sleep 3")` with a thread selected (§8.3): gdb won't let `$_shell` be overwritten, and a Python function standing in for it can't call the original (gdb 14 refuses; 17.1 hit an internal error).
- **`thread apply all` of an alias of `bt`** (`alias mybt = backtrace`) shows the parked threads; aliases of `shell`, `make`, `pipe` and `edit` run without a window, and of `frame`, `up` and `down` are done by realm-gdb.
- **`rt realm-thread`**, the list, is refused: the host's stack pointer is the parked thread's in a window, so that thread would be listed as running.
- **`watch` without `-l`** is refused there too: gdb ties the watchpoint to the parked frame, looks for that frame on the thread it checks, and deletes the watchpoint at once. The refusal gives the `rt watch -l EXPR` (or `realm-thread apply N watch -l EXPR`) to type instead, which watches the memory EXPR is in.
- **A register change made in a window doesn't last,** since the window puts the host's registers back, and realm-gdb says so: `rt set var $rbx = 1`, or a `set var` of a frame-0 variable that lives in a register, gets "'set' changed $rbx, which doesn't last". In an outer frame, gdb writes a register where an inner frame saved it, on the stack, if one did, and that change lasts. Where the window couldn't put the host's registers back, or the program was resumed meanwhile (§3.7), the warning saying so comes instead (`_kept_notes`).
- **An empty line** doesn't repeat `realm-thread N` or `realm-thread back` (`dont_repeat`).
- **Queries inside a window** take gdb's default answers, as `confirm` is off. `rt break FUNC` (or a plain `break FUNC` with a thread selected) of a function not yet loaded makes no pending breakpoint unless `set breakpoint pending on`; a plain one says so, telling it by `$bpnum` (`plain_break_pending`). `rt delete` deletes every breakpoint without asking.
- **gdb can't pass non-ASCII arguments to a Python command in the C locale,** so `rt print sizeof("é")` fails there, before realm-gdb sees it.
- **Refusals inside `rt`** add advice: "Run it without 'rt'", or, for a command that plain commands refuse too, "Run it after 'realm-thread back', without 'rt'". Selecting, going back and `rt` itself are refused inside a window. A refusal names the command that opened the window and the user thread shown ("refusing 'continue' in 'rt', where thread 5 has user thread 3 (0x...)'s registers until the command is over: the program mustn't run, or be let go of, meanwhile"), with a reason of its own for `generate-core-file`, `checkpoint`, `record` and `queue-signal`. `realm-thread apply all` stops at the first parked thread where realm-gdb refuses the command, and says so once (`select_refused`, `refusal_messages`).
- **Where it works:** the CLI, scripts and batch mode, MI's `-interpreter-exec console` and DAP's REPL (`mi_select`). Selections are per inferior, so `rt` in an inferior without one says which inferior has one.
- **Help.** `help realm-thread`, `help rt` and `help realm-thread apply` describe the commands, dedented for gdbs before 13, which show a docstring as it is (`inspect.cleandoc`); `help realm-thread` says that `rt COMMAND` pages, where plain commands don't (§3.9).

A nested prompt, where `realm-thread N` would read your commands itself at a `(realm 0x...)` prompt, would avoid typing `rt`. A prototype on gdb 9.2 and 16.3 showed rough edges: Tab inserted a literal tab instead of completing; Ctrl-C only took effect at the next Enter, and dropped that line; the up arrow recalled gdb's history, not the nested prompt's; and it needs a terminal.

### 3.9 Plain commands on a selected parked thread

While a parked thread is selected, in a console gdb session, plain commands act as `rt COMMAND` would, or are refused, as in the earlier designs, where `realm-thread N` showed a parked thread to every command until `back`. They are shown it through their hooks: a `hook-COMMAND` opens a window, and its `hookpost-COMMAND` closes it. An earlier attempt did this with a launcher that ran gdb on a terminal of its own and put `rt` in front of the right lines; it was set aside, as it had to guess from outside gdb who would read the terminal next, and inputs were found that defeated each guess (a program could even print a line that gdb then ran).

- **Commands that work with the selected thread or frame** (`_SHOWING_COMMANDS`; `plain_commands`, `plain_showing`) get a window for their whole duration:
  - `backtrace`, `info stack`, `frame` and its subcommands, `select-frame`, `up`, `down`, `up-silently`, `down-silently`, `info frame` and its subcommands, `info locals`/`args`/`registers`/`all-registers`/`vector`/`float`/`line`/`source`/`symbol`/`address`/`scope`/`display`, `list`, `print`, `call`, `output`, `printf`, `x`, `ptype`, `whatis`, `display`, `disassemble`, `find`, `set` (an assignment), `set variable`, `break`, `tbreak`, `hbreak`, `thbreak`, `dprintf`, `clear`, `tvariable` (whose initial value gdb evaluates at once);
  - and the other commands that evaluate an expression in the selected frame's scope, or take a location relative to it: `eval`, `init-if-undefined`, `print-object`, `dump` and `append` with their subcommands, `restore`, `mem`, `memory-tag` and its subcommands, `info vtbl`, `info common`, `info macro`, `info macros`, `macro expand`, `macro expand-once`, `break-range`, `trace`, `ftrace`, `skip`, `skip function`, `skip file`. `PREFIX *` in the list stands for every subcommand, at any depth (`_expand`);
  - their `hook-COMMAND` opens a window (`_plain_before`) that shows the selection, with its remembered frame selected, as `rt` does, after the same checks; their `hookpost-COMMAND` remembers the frame left selected, closes the window, and prints the notes `rt` would (`_plain_after`);
  - gdb runs its own command, as typed, so its output isn't collected: `frame N` prints through gdb's notification, and `x` and `list` repeat on Enter;
  - Ctrl-C works as usual in one typed at a terminal, or run by breakpoint commands there, until one of its calls has ended (§3.4): gdb runs it, not Python, so the window lets Ctrl-C through for it once open (`interruptible`), and a Ctrl-C that quits it leaves the window for the prompt that follows (`terminal.plain`: a long `disassemble` quits within seconds). Run from Python, from a script or in batch mode, where no prompt may follow, it is held until the command is over, and so on gdb 8.2 and 9.2, where one landing in a pretty-printer would kill gdb;
  - gdb's pager is off in these windows, as the output isn't collected and the pager waits in a nested event loop (§3.4), where gdb 15's posted closer (below) would run too (`_CallSettings(paging=False)`); `rt COMMAND` pages;
  - subcommands need hooks of their own (`frame level 3` runs `frame hook-level`), and `info stack` isn't an alias of `backtrace`; aliases (`bt`, `where`, `p`, `inspect`, `f`) and abbreviations share their command's hooks.
  - **`set var X = V`** acts as `print X = V` always did: it changes X on the parked thread. A variable on its stack keeps the change; one in a register keeps it only until the command is over, and realm-gdb says so; a thread-local variable is the host thread's own. Assigning to `$pc` or `$sp` changes only the window, and `set $var = 1` sets a convenience variable, as ever. (A hook can't tell `set $i = 0` from `set var x = 1`.)
  - **`eval`** evaluates its arguments with the parked thread shown, then runs the command it built, which, if hooked, closes `eval`'s window as one run after it, and opens its own.
  - **`break` without a location**, and `tbreak`, `hbreak`, `thbreak`, `dprintf` and `clear`, use the parked thread's selected frame; in frame #0 that is the resume point in `user_switch`, which every user thread passes on every switch. Breakpoints are inserted only when the program runs, so nothing is written meanwhile. The pending-breakpoint question takes its default answer, no, which realm-gdb then says (§3.8).
- **Commands that would act on the selected thread as it really is are refused** (`_ACTING_COMMANDS`, `_refuse_acting`, `plain_refused`): `step`, `stepi`, `next`, `nexti`, `finish`, `until`, `advance`, `jump`, `return`, `signal`, `queue-signal`, the `reverse-*` commands, `watch`, `rwatch`, `awatch`, `explore`, `thread apply`, `frame apply`, `faas`, `interpreter-exec`, `pipe`.
  - `pipe COMMAND | SHELL` (and `|`): gdb starts SHELL first, then runs COMMAND, whose own hooks would give it a window that stayed open for as long as COMMAND's output was blocked on SHELL, or, if COMMAND failed, until SHELL ended (`pipe x/400000gx $sp | sleep 20` would keep the parked SP and PC in the host for 20 seconds). `rt pipe` collects COMMAND's output, closes the window, then runs SHELL (§3.8).
  - `watch`: a watchpoint on a local is tied to its frame, which gdb looks for on the thread it checks, where a parked frame isn't, so it may delete the watchpoint early.
  - `explore` asks its questions at the terminal, which can't be done while the user thread is shown; its refusal suggests `print` or `ptype`.
  - The message says why and to run `realm-thread back` first, plus `rt COMMAND ...` for those `rt` can run on the parked thread (`_RT_COMMANDS`: `frame apply`, `faas`, `pipe`), and `rt watch -l EXPR` for the `watch` commands.
- **`python`, `guile` and `compile` run on the thread as it really is,** and so do `python-interactive` and `guile-repl`, saying so once a selection (`_NOTED_COMMANDS`, `plain_python_noted`): Python's frame API sees the host, while the gdb commands the code runs show the selection; `rt python ...` runs it all on the parked thread. Refused, a bare `python` typed at a terminal would leave the lines of its body to run as gdb commands, a `continue` among them (`terminal.body_lines`); and a Python script run by `source` or from a user-defined command runs on the host anyway.
- **`continue` ends the selection** (`_LEAVING_COMMANDS`): it drops the inferior's selections, saying "continuing; no longer selecting user thread ...", then runs (`plain_continue`). Inside a window it is still refused.
- **`thread N` ends it too** (`_SWITCHING_COMMANDS`), once it has switched, saying "switched to thread N; no longer selecting ...". `thread` alone, or naming the thread already selected, keeps the selection, and says so, as gdb may have printed the thread's own frame, which the next command won't show ("realm-thread: still selecting user thread 3 (0x...): plain commands show it, not thread 5 as it really is, until 'realm-thread back'."); a `thread N` that fails keeps it too (`plain_thread`).
- **`thread apply all`** (realm-gdb's own) runs gdb's `thread apply` with plain commands showing threads as they are (`_plain_suppressed`), so `thread apply all bt` and `taas` work.
- **A command that fails skips its hookpost,** so its window stays open. Three things close it (`_close_stale`, `plain_failed`): the next top-level prompt (`before_prompt`, and realm-gdb's prompt hook: below); gdb exiting (`gdb_exiting`, gdb ≥ 12); and the next hooked command, or realm-gdb command, that isn't part of the failed one.
- **`source` and `inferior` close it too** (`_CLOSING_COMMANDS`), as hooked commands that do nothing else. A command typed at the top level, or from `-ex`, runs from no Python frames, so any Python run after it would count as part of it (below): a Python script sourced after a failed one would see the parked thread (`plain_failed_top_level`), and `inferior N` after a failed `-ex` command would be undone when the window closed later.
- **Python's own ways in** close a failed command's window first, as a hooked command would:
  - **`gdb.parameter`,** which realm-gdb wraps (in gdb's C module too, where gdb 15 and 16's `gdb.with_parameter` finds it): else a script that caught the failure, then saved a setting with `gdb.with_parameter`, would save the window's value (`confirm off`, `scheduler-locking on`), and leave it for good (`plain_failed_settings.python_with_parameter`);
  - **`gdb.execute_mi`,** wrapped for §3.6's refusals too (`plain_failed_execute_mi`);
  - **Python's audit events** of starting another program (§3.7);
  - **Python's REPL** (`pi`): it gives no prompt event while it waits for a line, and before gdb 15 no posted closer runs, so a plain command that failed in it would leave its window open as long as the user stayed at `>>>`. The REPL's prompts, `sys.ps1` and `sys.ps2`, close such a window as Python asks for them (`_ReplPrompt`, `terminal.pi_failed`);
  - **`input()` and `sys.stdin`,** refused in a plain command's window (§3.8), read as usual when the code reading isn't part of the command, which then failed (a `code.interact()` console, `pdb`, a script's `input()` after its `gdb.execute("print X")` failed), the window closing first (`_NoTerminalInput.let`, `plain_failed_input`). A `pdb` made meanwhile, which keeps the `sys.stdin` it found, reads the real one once the window is closed.
- **A Python script run by `-x FILE.py`** runs no `source` hook. After a command run from no Python frames, Python whose outermost frame is a module's body counts as run after it, so the script's first hooked command closes the window (`terminal.plain_x_script`); until then, the script's own reads (`gdb.newest_frame()`) see the parked thread.
- **Another UI's prompt during a function call** (one realm-gdb doesn't see: §3.4) closes nothing: a call in progress means a command is still running (§3.3).
- **A prompt hook set after a selection** (`gdb.prompt_hook = ...`) would replace realm-gdb's; its `before_prompt` handler wraps such a hook again before gdb calls it (`plain_failed_at_prompt.prompt_hook_after`).
- **At the prompt,** gdb runs the `before_prompt` handlers, then `gdb.prompt_hook`. A handler connected after realm-gdb's, or the user's prompt hook, that ran a hooked command which failed would leave its window open at the prompt (seen on 13.2 to 17.1). realm-gdb's prompt hook, the last Python to run before the prompt, closes such a window before and after it runs the user's prompt hook with plain commands showing threads as they are, so that a user's hook that raises leaves nothing open either (`plain_failed_at_prompt`, `.raising_hook`). A `before_prompt` handler connected before realm-gdb's (from `~/.gdbinit`, say) still sees a failed command's window.
- **Where no prompt event comes,** gdb's event loop does, from gdb 15: each plain window posts a closer (`gdb.post_event`, `_post_close`) as it opens, which closes it then if a failed command left it open (not during a call made in it, when gdb runs its event loop too, nor between a call's stop and its `inferior_call_post`: §3.3). That covers a plain command that fails in breakpoint commands at a stop in the background (`continue &`, whose prompt is already shown), in a `hook-stop`, or in a posted event, whose window would otherwise stay open while gdb sat idle (an attached program aborted when gdb was killed then: `plain_failed_posted`, `terminal.plain_failed_background`); and a window left open by a Ctrl-C in MI and DAP, which have no prompt event (`window_left_open_mi`). gdb 9 to 14 die as they exit with a posted event left (a SIGSEGV or abort, after letting go of the program), as in `-batch` or after a script's `quit` (`plain_batch` died so on 12.1 to 14.2), so realm-gdb posts only where gdb has `gdb.interrupt`, which came with gdb 15's fix (`_post`).
- **How "part of" is told.** Each window records the Python frames its command was run from (`_outer_frames`), and the innermost one's `f_lasti`.
  - A command run as part of another, by a pretty-printer's `gdb.execute` say, runs from newer Python frames stacked on those, which haven't moved; a command run afterwards doesn't: no Python at all, the same frames, or ones that have moved on.
  - During a function call, nothing is closed: only the command making it can run commands then. (gdb 14 and later run no `hook-stop` for calls; gdb 13 runs a user's for a call that stops, in the window, where its `continue` is refused: `window_hook_stop`.) Nor is a window opened then: a dprintf hit in a call (an `if` condition's) runs `printf`, which would show the selection in the middle of the call, and couldn't print the called function's own variables (`plain_dprintf_in_call`).
  - A command run as part of another *without* Python, as `thread apply` and `frame apply` run theirs, can't be told from one run after it. That is why those two are refused, rather than shown: `thread apply` would need its inner commands to show threads as they are, and `frame apply` the window to stay open across them.
  - Until a window left open closes, its guards refuse resuming or letting go, as in any window.
- **Where plain commands don't show a selection** (`_plain_off_why`), nothing is refused either, and `realm-thread N` says why (`rt` still works):
  - **MI and DAP sessions** (`mi_plain`): MI's own commands run no hooks, so after a failed `-interpreter-exec console` command an IDE's `-exec-continue` would resume with the window open (seen on gdb 12.1).
  - **Batch mode without `gdb_exiting`** (gdb < 12): gdb would let go of the program at the end with a failed command's window open. With gdb ≥ 12, batch mode works (`plain_batch`).
  - **A second UI** (`new-ui`), whose MI commands could come while a window is left open (`mi_new_ui_plain`): found from `hook-new-ui`, from `-ex new-ui` (or an abbreviation, `-ex "new mi ..."`) on gdb's command line, and, on Linux, from a terminal or named pipe gdb has open besides its standard streams (`_other_terminal`, checked at each selection, and named). A pseudo-terminal's master side doesn't count, nor a container's `/dev/pts/ptmx`: test drivers leak those.
  - These are judged from gdb's command line (`/proc/self/cmdline`, or `ps`), with gdb's options taken as gdb's `getopt_long_only` takes them: an exact name, or else the one option a word abbreviates (`--interp=mi`, `-interp mi2`, `--batch-s`, `--eval=new-ui ...`), with its value after `=` or as the next argument; nothing after `--args`, gdb 18's `--no-escape-args`, or `--`. An option realm-gdb doesn't know turns plain commands off. By full names only, `gdb --interp=mi` would pass for a console session, and `-exec-continue` after a failed command crashed the program (`session_options`).
- **The user's own hooks** are kept, with realm-gdb's check (§3.6), so showing commands show the selection with them too.
- **The TUI** draws its register window and status line from the selected thread and frame between commands, when the host has its own registers again: so they show the host, while the command window's output shows the parked thread. Its source and assembly windows can be left at a location a command showed (the parked thread's frame #0 after `realm-thread N`, until a frame of the host's is shown). realm-gdb can't change that, and says so once, when a thread is selected with the TUI on (`info win`), or when the TUI is turned on with one selected, where gdb tells (`gdb.events.tui_enabled`, gdb ≥ 16). It doesn't check at each prompt: a command run there, before gdb 10, becomes the one an empty line repeats (it broke `x`'s repeat on 8.2, `terminal.plain`). TUI screens were checked by hand with a terminal emulator; no automated test covers them.
- **When gdb loses its selected thread** (the program died in a function call: `print (void)_exit(3)`, or `kill -9` during one), `gdb.selected_thread()` raises `SystemError`. realm-gdb's commands say "no thread is selected", and drop the selection, rather than raise; and they don't switch threads then, which couldn't be undone, and would leave a dead thread selected, after which every command failed, `kill` included (`window_program_died`).
- **What isn't covered:** commands written in Python (`gdb.Command`) see threads as they are through Python's API, though the hooked commands they run with `gdb.execute` show the selection, and those that would act on the host are refused; `edit *EXPR` evaluates in the host's frame; the TUI's windows show the host between commands; `inferior N` back into an inferior with a selection prints the host's frame.

### 3.10 Where windows aren't used

`_how_shown` returns a reason, and every command that would show a parked thread prints it with advice:

- **Non-stop mode,** even with every thread stopped: realm-gdb would have to change a stopped thread's registers while other threads may run. Advice: write a core file with `gcore` and load it in another gdb, or debug with `set non-stop off` (`non_stop`).
- **A running program** (`continue &`). Advice: `interrupt` (`running_in_background`).
- **Another inferior's program running** (`run &` in inferior 2): a window's function calls disable breakpoints, which are every inferior's, so that program would run past its breakpoints, and its exit cut the call short. Advice: `interrupt -a` (`window_other_inferior_running`).
- **Record/replay.** Register writes would spoil the execution log. Advice: `record stop`, or `gcore` (`window_record`). A command in `realm-thread apply all` that began recording stops it before the next parked thread (§3.1).
- **`may-write-registers` off** (gdb ≥ 14 allows it with a live process): showing writes registers, which would fail with gdb's "Writing to registers is not allowed", and the check of the extended registers take that for AMX. Advice: `set may-write-registers on`, or `gcore` (`window_may_write_registers_off`). One turned off by a command inside a window is another matter (§3.6).
- **A thread of gdb's started from Python that doesn't block Ctrl-C,** where a Ctrl-C it took during a window would kill gdb (8.2, 9.2, and 17 and later) or quit it in the middle of popping a call (10 to 16) (§3.4). Advice: have it block SIGINT as it starts (`signal.pthread_sigmask`, or start it as a `gdb.Thread`, gdb ≥ 14), or `gcore`.
- **realm-gdb couldn't install its guards** (§3.6). Advice: load realm-gdb.py again, or `gcore`.

With a parked thread selected, a plain command refused for one of these reasons says it wasn't run, and that `realm-thread back` first would run it on the thread as it really is (`plain_refused_advice`). `realm-thread` still lists the user threads in these cases, and `thread apply all bt` prints a "not shown" section with the count and the reason.

**The registry.** Where realm-gdb can't read the user thread registry at all (`Realm::user_thread_registry_head`: librealm without its debug information, or gdb's `--readnever`), `realm-thread`, `realm-thread apply` and a lookup by number say so, quoting gdb's error (`registry_unreadable`). Where gdb had the registry's symbol for the process, and no longer has (`nosharedlibrary`), they say that instead, and so does a plain command with a parked thread selected, as it drops the selection, rather than that the thread "is no longer a Realm user thread" (`registry_dropped`; `sharedlibrary` brings them back). The registry's symbol missing altogether (no Realm in the program, or librealm not loaded yet) is said so too ("inferior N's program has no Realm user thread registry"). `thread apply all bt` prints a "not shown" section, with the reason, where the registry couldn't be read or its symbols were dropped, and says nothing for a program with no Realm. With no process, `realm-thread` says so and names an inferior that has user threads, and neither it nor `thread apply all bt` leaves another inferior selected (`list_other_inferior`). A link to memory that can't be read (a crash may leave one) ends the list, and `realm-thread apply all`, after the threads before it, saying so (`registry_broken`); a link that loops back is reported as a corrupt registry (`registry_loop`).

## 4. Core files: views

Core files can't take register writes, so there a parked thread is shown by a Python unwinder (`_ParkedThreadUnwinder`), as an earlier design did in live processes too. It claims the host's innermost frame (the *host frame*) and reports the parked thread's saved context as that frame's caller's registers: frame #0 stays the host's own frame, and the parked stack starts at frame #1. A view is the record that it does so on a host (`_views`).

- **Claiming the host frame.** gdb ≥ 11 tells unwinders the pending frame's level (`PendingFrame.level()`), and the unwinder claims the host frame's, if its PC and SP are still the host's. Older gdbs don't, so there a view is *armed* just before gdb rebuilds the host thread's frame cache, and the unwinder claims the first frame it is then asked about (the *arming scheme*); where the host might not be at that frame, the view is hidden until checked.
- **Its frame ID.** gdb stops unwinding at a caller whose frame ID is inner to its callee's, and the parked stack can be anywhere relative to the host's, so the host frame gets an ID at the parked thread's SP. As gdb finds frame #0's arguments and locals from that ID's stack address, it reads them at the parked thread's SP, so they are wrong while a view is shown (below).
- **The marker line.** Frame #0 belongs to whatever the host was running, and printed as it is it would read as the caller of the parked frames. So backtraces draw it as a marker, `#0 <parked Realm user thread 0x...> ()`, through a frame filter (`_frame_filter`). Any frame filter makes gdb print the backtrace with its Python frame printer rather than its own, and that printer's differences are fixed:

- `_frame_locals` lists locals as gdb's own printer does;
- `_printing_lookup` prints entirely optimized-out values as `<optimized out>`;
- `bt N` and `set backtrace limit` are adjusted for the marker line;
- `_frame_filter` is turned on only while a view is shown;
- the DAP cache is reset when views come and go;
- the arming scheme serves gdb < 11.

`realm-thread N` and `realm-thread back` keep views shown and nested (`core_show`, `core_show_nested`); `thread apply all bt` and `realm-thread apply` use temporary views. As in a live process, a kept view gets the prompt's reminder and the list's `*`, and selecting it prints its frame.

- **`thread apply all`'s own section,** gdb's threads, shows them as they are, with no view, as in a live process (`_ViewsOff`, `core_thread_apply_all_shown`).
- **`thread N`** leaves a view on its thread. `thread` to that thread prints gdb's frame #0 of it, the host's own, so realm-gdb says the thread still shows the parked one (`core_thread_note`). `rt` and `realm-thread back` on a thread without a view name the thread that has one.
- **Errors.** A parked stack a view can't unwind (the unwinder disabled with `disable unwinder`, say) is "not shown", with that hint, and `rt COMMAND`'s errors are gdb's own, not a Python exception (`core_rt_error`). A view is dropped if its thread ever runs, as when `run` replaces the core with a live process.

**Dropped, because a core file never runs and can't make calls:** refusing calls while printing, and with it the gdb 8 rule about pretty-printers; `realm-lock-calls`; forced-return undo; doomed views; posted events and the exit-crash workaround; the version checks for gdb 11–13 and ≤ 14.

**What remains for core files:**

- frame #0's own values are wrong while a view is shown (above). Only `frame 0`, `info frame`, `bt no-filters`, and `print` in frame #0 show them; the marker line doesn't. There are no calls, so this is a (b) issue only.
- aarch64's d8–d15 show as `<optimized out>`;
- the Python frame printer's remaining cosmetic differences: no "No locals." lines, `??? () at LIB` for gdb's `?? () from LIB`, and parameter types in function names on gdb 9;
- a false warning of gdb 10.2's (§8.4).

**The 22.04 jobs and AMX,** the evidence for refusing calls where gdb can't write the extended registers (§3.3), and for leaving out the 22.04 jobs:

- **The 22.04 x86-64 jobs (gdb 12.1) failed on some runners:** three times, with RelWithDebInfo and with Debug, every test that writes the extended registers (x87, SSE, AVX) failed with "Couldn't write extended state status: Bad address", 87 tests in all; the same jobs passed in other runs. It is gdb 12, on a runner with AMX turned on; neither the CPU model nor realm-gdb decides it.
  - **gdb's side.** gdb 8.2 to 13.2 write the extended registers by reading a fixed 2,696 bytes (`X86_XSTATE_MAX_SIZE`) with `PTRACE_GETREGSET`, changing them, and writing them back (`amd64_linux_nat_target::store_registers`). gdb 14 sizes that buffer from CPUID (`tdep->xsave_layout.sizeof_xsave`).
  - **The kernel's side.** Linux refuses, with EFAULT, a `PTRACE_SETREGSET` of `NT_X86_XSTATE` that isn't its whole XSAVE area. With AMX on (XCR0 bits 17 and 18), that area is 11,008 bytes.
  - **realm-gdb's writes.** The general registers are written with another call (`PTRACE_SETREGS`), so showing a parked thread works. realm-gdb saves and puts back only the registers of gdb's own "save" group for the target, never one the CPU lacks.
  - **The CI evidence.** A probe ran on 75 runners (plain gdb, no realm-gdb). Four had AMX on, all with XCR0 0x600e7: two of the seven Xeon Platinum 8573Cs, and two Xeon 6973P-Cs. The other 71 had an XSAVE area of 2,688 bytes or less: AMD EPYC 7763, 9V74 and 9V45, and Xeon 8370C, besides the five other 8573Cs. On each of the four, gdb 12.1 wrote `$rax` but failed to write `$xmm0` or make a function call; gdb 15.1 and 17.1 did all of it; a raw `PTRACE_SETREGSET` of 2,696 bytes failed with EFAULT, and one of 11,008 succeeded.
  - **The consequence.** On such a machine gdb 13 and older can't make a function call at all, as putting the caller's registers back writes the extended ones, and a window couldn't put back what a call changed. A `_put_back` that stopped at the first register it couldn't write would also leave `$mxcsr` and `$orig_rax`, and with `$orig_rax` as the call set it the system call the thread had stopped in wouldn't be restarted: the attached program died of SIGABRT after gdb left (`window_signals.HUP_in_call`, `TERM_in_call`).
- **The shim is faithful:** gdb 12.1 under it fails the same 86 suite tests as that CI job, all but CI's terminal test. Under it, plain gdb's failed call from a thread stopped in a system call leaves `$orig_rax` at -1: a test program's `nanosleep` then returned error 516, and Realm's test program died of SIGABRT on `continue`. realm-gdb without calls makes no extended-register writes (`bt`, `thread apply all bt full`, `realm-thread apply`, a selection with plain commands, `info all-registers`); a window's call is refused, and the program exits normally.
- **In CI the 22.04 jobs are left out,** rather than made to skip the tests that make calls where gdb can't write those registers, which would fail there as refused calls.
- **An older case.** gdb 7.12 failed the same way on AVX-512 CPUs (Debian bug #898048).

**FreeBSD in a VM** (`freebsd-vm.sh` in a container with `/dev/kvm`): 354/354 CTest entries passed on 15.1 (Debug) and 14.5 (RelWithDebInfo), with an earlier version of the suite; the skips are those of §8.9, plus `optimized_out` and `marker_optimized_out`, whose compiler kept every value. CI's FreeBSD jobs run the suite since, and the VM single tests.

## 8. Open issues and known limits

Each limit found by trying says how it is known: verified (checked to hold, with the script as it is), reproduced (the failure made to happen, on the gdbs named), or reasoned (from the code or gdb's sources, not tried). Those that follow from the design itself (what no hook sees, what a window can't change) are stated as such.

### 8.1 Decisions for the project

1. **Realm's guard page** is above each user-thread stack instead of below it, in `UserThread::start_thread`. A stack overflow, a task's own or a debugger call's, silently writes over whatever is mapped below. The fix is small: mprotect the bottom page and start `uc_stack` above it.
2. **Navigation outside console sessions.** Plain commands show a selected parked thread only in console sessions (§3.9). MI and DAP sessions need `rt` after `realm-thread N`, and IDE call-stack panes never show parked threads.
3. **A Realm-side check that a parked context was resumed by Realm.** Realm sets `ThreadLocal::current_user_thread` to the thread it switches to before each `swapcontext`, so right after the two user-thread `swapcontext` calls in `UserThread::user_switch` it could check that the thread now running is the one that switched out, and abort with a message if not ("user thread %p was resumed on this thread by something other than Realm (a debugger's register window left behind?)"). That catches every way a host can come to run a parked context that the window code can't refuse or cover: gdb dying where `PTRACE_O_EXITKILL` doesn't apply (remote targets, FreeBSD with `kern.kill_on_debugger_exit` at 0), a resume past the refusals that §3.7's SIGINT can't stop (a remote target, `handle SIGINT` changed), a detach by such a path. The program then aborts before it touches any of Realm's state, rather than corrupting itself. Tried as a 24-line change to `threads.cc`: kill -9 of gdb in a window, and a bypassing `-exec-continue`, both ended in that abort, and the suite found no false positives (16.3, 9.2). It costs a function call and a thread-local read per switch, and doesn't cover gdb dying during a window's call, which returns to its breakpoint on the stack (`PTRACE_O_EXITKILL` does).
4. **Ctrl-C during a window's calls on gdb 8.2 and 9.2,** where a call made from Python holds Ctrl-C (§3.4). On 9.2 realm-gdb's deadline unwinds a hung one after 10 seconds (§3.3); on 8.2, which keeps Python's lock through it, only SIGKILL ends one (which kills an attached program, §3.7). A Python thread that took Ctrl-C (`sigtimedwait`) while every other thread blocks it, and passed it to the call as gdb does, would let such calls be interrupted at once. Tried (about 150 lines; it found a CPython 3.8 bug, `sigtimedwait` returning an uninitialized siginfo when interrupted at its deadline), it worked on 9.2, 12.1 and 16.3, but isn't adopted: a second mechanism for Ctrl-C beside §3.4's, for two old gdbs, and on 8.2 it can't help calls made from Python either.
5. **Choices made here that could go the other way:**
   - **`python` and `guile` run on the thread as it really is** while a thread is selected, with a note, rather than in a window (§3.9). A window would let Python's frame API see the parked thread, but code run there could do anything a window mustn't (start programs, read the terminal), unseen by hooks; `rt python` runs it in one, when the user asks.
   - **`thread apply` and `frame apply` are refused** while a thread is selected, since their inner commands can't be told from later ones (§3.9). `thread apply all` and `rt frame apply` work.
   - **A register write to a parked thread doesn't last** (§3.8). Writing changed callee-saved registers into its saved context would make `set var $rbx = 1` take effect when it resumes, and a mistaken `set $pc` too.
6. **Tried or proposed, and not adopted:**
   - **`rt finish`,** to run until a parked frame returns: read the caller frame's PC and SP in a window, then, with the window closed, `tbreak *PC if $sp == SP` and `continue`, whose hook drops the selection. A prototype stopped exactly as the frame returned, though other tasks pass the same PC; from frame #0 it stops as the user thread is resumed. The same idiom gives a breakpoint for one user thread (`if $sp >= base && $sp < base + size`). A new feature, not a fix.
   - **Stopping a window's calls at Realm's blocking functions** (`Event::wait`, `user_switch`), so that a call that would switch user threads (§8.2) is abandoned first: at `Event::wait`'s entry it would refuse legitimate calls on triggered events, which return at once (the early-out is inside `wait_faultaware`), and later points (`thread_blocking`, `wait_slow`) come after state has changed (a waker registered, a doorbell prepared).
   - **A watch on SIGTERM and SIGHUP for the whole window,** sending gdb a Ctrl-C a second after one came, so that a slow command can't hold gdb's exit for long (§8.2): a thread for every window, for what Ctrl-C now does on gdb ≥ 10.
   - **A note where gdb's death isn't covered** (a remote target; FreeBSD with the sysctl at 0): only the Realm-side check (3.) would cover them.
   - **`gdb.interrupt` sending a real SIGINT on gdb 15 and 16,** as gdb 17's does: fault injection found nothing for it to fix (§8.2).
   - **Not prototyped:** on FreeBSD, finding a second UI from gdb's own file descriptors (`fstat`, `isatty`) and Python threads that don't block SIGINT from `kern.proc` (§8.2, §8.9); refusing ctypes' look-ups of `fork`, `exec*`, `system` and the like in a window (Python's `ctypes.dlsym` audit event, which comes only at the first look-up on each library object); interrupting a window's call, with §3.7's SIGINT, when another thread resumes during it (§3.4); closing a failed plain command's window sooner, with closing hooks on more commands (`maint print *`), at the cost of a longer check of the hooks as each window opens.
   - **Fewer MI notifications** (§8.6), by setting the window's settings as its first call begins rather than as it opens; **a parameter for the call timeout** (10 seconds, which a user's lower value overrides); **a column in `realm-thread`'s list** with each thread's innermost frame outside Realm (about 12 ms per parked thread); **`thread N` of the host ending the selection**; **re-wrapping `rt`'s collected output** as gdb wraps long lines (§8.5).

### 8.2 Safety: what can still corrupt the program or lose gdb

- **gdb dying with a window open** (kill -9, a crash, an internal error, an abort) kills an attached program, on Linux with gdb debugging it natively (§3.7; verified, `terminal.attach_gdb_killed`), and on FreeBSD by the kernel: the program is lost, as one gdb started is, but not corrupted. gdb's own crash bugs count: `rt maintenance canonicalize`, with no argument, segfaults gdb 17.1 as it does without realm-gdb, but with the window open; and `maint set internal-error quit yes`, run by a command in a window, would have an internal error there quit gdb (reasoned).
  - **Not covered:** a remote target (reproduced with gdbserver 9.2: with gdb killed in a window, gdbserver stayed attached with the program stopped, and the program ran on with the parked context once gdbserver itself went away); and, reasoned, FreeBSD with `kern.kill_on_debugger_exit` at 0, and Python without ctypes. A window whose host ran, and was still running as it closed, keeps the option, so gdb's death then kills the program (§3.7).
  - A window usually lasts tens of milliseconds, but longer in these cases:
    - **A slow command:** `bt full` with pretty-printers that call functions, a large `x`. Ctrl-C cuts it short on gdb ≥ 10, in `rt` and `realm-thread apply` and in a plain command typed at a terminal, until one of its calls has ended (§3.4); on 8.2 and 9.2 it is held, as a Ctrl-C landing while Python ran would kill gdb with the window open. SIGTERM and SIGHUP wait for the command's end: one that never ends (a looping pretty-printer) can be ended by Ctrl-C (gdb ≥ 10), or else only by SIGKILL, with the window open.
    - **A function call:** up to 10 seconds before it is unwound (12 where gdb's own timeout should have done it, §3.3); on gdb 8.2, one made from Python until SIGKILL. SIGTERM and SIGHUP wait for it; a call that waits for the terminal (`rt print getchar()`) is such a call.
    - **A plain command that failed:** its window stays open until the next prompt or hooked command (§8.3), through any unhooked commands in between in a batch script or an `-ex` sequence (`maint print registers`, other extensions' commands, a Python script run by `-x`).
    - **A plain command whose output is blocked** (§8.3), **a plain command's `$_shell(...)`** (§8.3), and **a program that Python code in a window starts through ctypes** (§3.7).
    - **SIGTTOU, SIGTTIN and SIGSTOP** aren't held: a gdb in the background of its terminal that writes to it (with `stty tostop`) or reads it during a window, or a SIGSTOP, stops gdb with the window open. That only pauses gdb, with the program stopped too, and the window closes once gdb is continued; caught, as the other held signals are, SIGTTOU would have gdb's write retried and stopped again, without end (reasoned).
- **gdb 8.2 and 9.2 with Python 3.8** (9.2 is Ubuntu 20.04's) can die when Ctrl-C lands while Python runs a command, any command: without realm-gdb, a Python loop of `gdb.execute("thread apply all bt 1")` killed 9.2 after 3 SIGINTs (a SIGSEGV in `_PyOS_InterruptOccurred`) and 8.2 after 9 (`std::terminate`); 10.2 took 2,805. One SIGINT during a loop of `realm-thread apply all bt 1` killed 9.2 in 2 of 8 tries with Ctrl-C unblocked, and the attached program died with it; with it blocked in windows (§3.4), all 8 ended in a plain Quit (verified). It still gets through during the calls that a gdb command makes itself, with no Python beneath (a plain `print f()` with a thread selected), as it must:
  - once in about 500 Ctrl-Cs that `terminal.plain_ctrl_c_calls` typed into plain `print f()+f()+...` commands, 9.2 aborted (SIGABRT), and twelve runs again passed (reproduced once). Such a call has Ctrl-C let through from the end of realm-gdb's handler of its `inferior_call_pre`, a few Python instructions before gdb takes over, and one landing there can leave Python's trip set as gdb leaves Python;
  - gdb 9.2 also aborts on Ctrl-C during a pretty-printer's call in `bt full` without realm-gdb, and the attached program then dies.
- **A resume that gets past the refusals:** a hook replaced inside a window (`rt source FILE` of a file that defines `hook-continue` in an `if` block, or `rt python gdb.execute("define hook-continue\n...")`, then `continue`), a reference to `gdb.execute_mi` that `_rebind` can't reach, MI's own `-exec-continue` with registers left. Unstopped, the program aborted (reproduced on 9.2, 12.1 and 16.3); the host is stopped before it runs, its registers put back, and the program runs on (§3.7; verified, `window_bypass_stopped`, here and in CI, FreeBSD's jobs included). What remains:
  - where it can't be stopped so (a remote target; `handle SIGINT` other than `stop nopass`; no ctypes), realm-gdb only warns that the program may crash;
  - the program's other threads run until gdb stops them, and the host may stop at its breakpoint again (reproduced; the window's note says so); a signal that gdb passes to the host as it resumes it is lost (reasoned);
  - ptrace through ctypes, Python's `RemoteTargetConnection.send_packet` (gdb ≥ 13) on a remote target, and a detach by a path that runs no hook get no event at all.

  Rechecking the hooks after each `gdb.execute` that defines one, by wrapping it, isn't done: the wrapper's frames would count as realm-gdb's code, and hold Ctrl-C in the user's own Python loops (§3.4).
- **Ctrl-C on another thread.** Ctrl-C is blocked on gdb's main thread only. gdb's worker threads, DAP's, and Python's `threading` threads started once realm-gdb has loaded block it (§3.4); a Python thread started before that, with `_thread`, or by a C extension, that doesn't takes one during a window, and kills gdb (8.2, 9.2, 17 and later) or quits it wherever it is (10 to 16), in the middle of popping a call, say. So parked threads aren't shown while such a thread runs (§3.10). Off Linux, without `/proc`, such threads can't be found, and a window opens all the same.
- **`gdb.interrupt()` on gdb 15 and 16** sets gdb's quit flag itself, sending no SIGINT, so blocking SIGINT doesn't keep it out of a window's teardown; DAP's `cancel` uses it (§3.4). Fault injection, 2,700 calls of it placed before realm-gdb's own commands during windows on 15.1 and 16.3, quit all 60 commands and left no setting, breakpoint, register or window behind, and the teardown retries each step after a KeyboardInterrupt (§3.4). The live race wasn't reached: a Python thread calling it every few milliseconds deadlocks plain gdb 16.3. From gdb 17 it sends a real SIGINT, which the blocking holds.
- **A Ctrl-C in the middle of popping a call gdb makes as it sets up a window's** (`malloc`, for a string argument) isn't kept out, as the window's own call has Ctrl-C let through by then (§3.4). It can leave that call's breakpoint in the parked thread's stack, which is found as the window closes, and then keeps the program from running (§3.3). Reasoned, not seen: it needs a Ctrl-C microseconds wide.
- **A second UI** could send MI commands, which run no hooks, while a failed command's window is open, or during a function call in any window (§3.4). Plain commands turn off, and calls in windows are refused, once realm-gdb sees one, but it sees one only from `hook-new-ui`, `-ex new-ui` on gdb's command line, or (Linux) an extra terminal or named pipe gdb has open: not one opened by a script before realm-gdb loads, on FreeBSD, nor, anywhere, one on something else (a regular file).
- **Bare `python`, `guile` or `compile code` built by an `eval` with arguments to format** (`rt eval "py%s", "thon"`), whose text no hook sees, gets past `rt`'s refusal (§3.8): at a terminal it would read the terminal with the window open, and in a sourced script it takes the script's following lines as its body ("name 'kill' is not defined").
- **The user's hooks, defined after realm-gdb loads where gdb runs no hooks** (from Python with their body, or in a block), replace realm-gdb's own until the next window opens, the next `define`, or the next prompt with registers left, any of which puts its check back (§3.6). One defined inside a window lets that window's command through, and what it lets run is stopped as above. Such a later `hookpost-print` leaves `print`'s window open until the next prompt or hooked command.
- **If a host's registers can't be put back,** or a function call left stopped can't be popped (§3.3), CLI commands that resume the program or let go of it are refused until `realm-thread back` succeeds; `kill` isn't. Function calls are refused too, but on gdb 8, which only warns (§3.6). This was seen only where gdb 12 could write no extended registers (§6.5), and calls are refused there (§3.3). The refusal applies even when the registers left over can't matter (vector registers at a function's entry or in a system call), and there is no way to accept them and carry on, short of `kill`.
  - **A call stopped in an inlined function** can't be popped on gdb 8.2 to 16, whose `return` refuses whenever the newest frame is an inline frame ("Can not force return from an inlined function"); gdb 17 checks the selected frame instead. Reproduced on 9.2 and 16.3 with a breakpoint made during the call in an inlined function: the program could then only be killed. Such breakpoints are disabled for the call now (§3.3), and nothing else is known to stop a window's call there.
- **Function calls in a window** run on the host thread, on the parked thread's stack (§3.3):
  - **Stack:** they start just below the parked SP. With no guard page below Realm's stacks (§8.1), the 64 KiB headroom check doesn't stop a deep call from writing over whatever lies below.
  - **Other threads:** every other thread is held, except, on gdb 14 and older, one the function itself starts (`pthread_create`), which gdb lets run until the next stop; realm-gdb then warns that a thread is resuming during the call. A function that waits on another thread (a lock it holds, a condition variable) hangs until it is timed out, or Ctrl-C, and is unwound.
  - **Unwound calls** (on a signal, a timeout, an escaping exception or Ctrl-C) can leave the program inconsistent, with a lock taken or an update half done, as any gdb call can.
  - **Breakpoints:** every user breakpoint, those made during the call included, is disabled while a call runs, so a called function can't be debugged.
  - **Settings:** a command in a window can change those that aren't about calls, and they stay changed until the window closes. (`rt with confirm on -- delete` doesn't ask, though: `gdb.execute(..., to_string=True)`, as `rt` runs it, answers queries as in batch mode. It deletes every breakpoint.)
  - **A refused call let through** by may-call-functions turned back on is abandoned before it runs, though gdb's message says "When the function is done executing, GDB will silently stop it". realm-gdb's note says so.
  - **Thread-local storage:** they use the host thread's: errno, malloc's per-thread cache, and Realm's thread-locals such as the current processor and task. If the host stopped inside malloc holding its arena lock, a call that allocates hangs, as it would on that thread without realm-gdb.
  - **A call that switches Realm user threads** (one that waits on an event, say) does so as the host, whose thread-locals it has, so Realm saves the host's context with its SP on the parked thread's stack. The other threads are held, so the call hangs until it is timed out and unwound, but Realm keeps what it did meanwhile. Reproduced: a parked thread's `Realm::Event::wait()`, called from a window, was unwound at 10 seconds, and at the next `continue` the program died of Realm's assertion `Doorbell::prepare(): prev == STATE_IDLE`. Calling such a function from gdb is unsafe on any thread (§8.1, 6.).
- **Changes made through a parked thread last when it resumes:** `set var X = V` or `print X = V` on its stack, and a register write in an outer frame, which gdb puts where an inner frame saved that register. That is gdb's usual meaning, but plain commands make it as easy as browsing. With frame #0 selected, an assignment to one of `user_switch`'s own variables changes what it does when the thread resumes.
- **rr and remote targets.** realm-gdb tells record/replay from `maint print target-stack`, where rr shows as an ordinary remote target, so register windows would write registers during an rr replay (untested).

### 8.3 Plain commands with a selected parked thread

- **Where they don't show it:** MI and DAP sessions, after a second UI, and batch mode before gdb 12 (§3.9). There, plain commands show the host as it really is, under the `[realm-thread N]` prompt, and nothing is refused; `realm-thread N` says so once.
  - From `ps`, which splits arguments that contain spaces (`-ex 'foo -s' --interpreter mi` becomes `-s --interpreter`, and `mi` a program), every word is also searched for an interpreter option and `new-ui`, which can only turn plain commands off, saying realm-gdb can't tell.
  - A terminal or named pipe that gdb inherited, leaked by whatever started it, turns them off too, naming it, and refuses function calls in every window for the rest of the session, as a second UI does (§3.4).
- **Commands that aren't hooked act on the host as it really is:** commands written in Python (`gdb.Command`), but realm-gdb's own; `edit *EXPR` (`rt edit *EXPR` works; bare `edit` uses gdb's source position, which the parked frames set); `if` and `while` conditions (in scripts and user-defined commands these are control commands, which run no hooks; typed, a `while` condition is shown the parked thread only the first time, the first command of its body closing the window); `info threads` and `thread`, by design; the frame-dependent `maint` commands (`maint print registers`, `raw-registers`, `cooked-registers`, `frame-id`, `maint agent`, `agent-eval`); `inferior N` back into an inferior with a selection, which prints the host's frame (selections are per inferior); `thread N` of the thread already selected, which prints the host's frame but says the selection is kept. `rt taas` and `rt tfaas` label the parked thread's output with the host's "Thread N (...)" header.
- **Refused while a thread is selected** (§3.9): resuming and stepping, `queue-signal`, `watch`, `thread apply`, `frame apply`, `faas`, `interpreter-exec`, `pipe` and `explore`. A script that uses one of them with a thread selected stops there. `continue` and `thread N` end every selection in the inferior, not just the latest.
- **Settings in each window:** the pager is off, so long output doesn't page (`rt COMMAND` pages); queries take their default answers, so `break` makes no pending breakpoint unless `set breakpoint pending on`, which realm-gdb then says.
- **A failed command's window stays open** until the next prompt or hooked command (§3.9). That interval only exists without a prompt: `-ex` sequences, batch scripts, Python that catches the error. Meanwhile:
  - **Registers:** unhooked commands see the parked registers on the host: `maint print registers`, Python's frame API in a script run by `-x`, other extensions' commands. (`source`, `shell`, `python`, `info threads` and the other hooked commands close the window first.)
  - **In the background, before gdb 15,** a plain command that fails in breakpoint commands at a stop in the background (`continue &`), in a `hook-stop`, or in a posted event, leaves its window open while gdb sits at its prompt, with SIGTERM held, until the next command (§3.9).
  - **Settings:** the window's show (`show confirm` says off), and apply: with its `pagination off`, an unhooked command's long output doesn't page there (24,000 lines of `info functions Realm::`, after a failed command in `-x FILE.gdb`, on a 24-line terminal; had gdb been killed as that output blocked, the attached program would have died). A change to one of them stays (§3.3).
  - **Input and signals:** SIGTERM and SIGHUP are held, and Python's `input()` is refused to code that is part of the failed command; code run after it closes the window first, and reads (§3.9).
- **The "part of" test can be fooled the safe way.** Python run after a failed top-level command, other than a sourced script or a `python` command (which close the window), counts as part of it (§3.9): a convenience function in an `if` condition, another extension's command. Its hooked commands then run nested in the old window, still showing the selection; its `realm-thread back` is refused until the next prompt; its `gdb.execute_mi('-exec-continue')` is refused (§3.6).
- **`break` in frame #0** is at the resume point in `user_switch`, which every user thread passes on every switch.
- **User-defined commands** get a window per inner command. A refused inner command stops the user-defined command.
- **`$_shell(...)`** in a plain command (`print $_shell("cmd")`, gdb ≥ 14) runs its shell command with the command's window open (§3.8).
- **`$_gdb_setting(...)`** in a window reports the window's `confirm`, `pagination` (off in a plain command's window), `multiple-symbols`, `unwindonsignal` and the like, so the gdb manual's idiom that saves one and sets it back, run with a parked thread selected, leaves the window's value; the five settings set only for calls are the user's (§3.3).
- **Completion** (TAB, `complete`) runs no hooks, so it completes names in the host's scope: `print chain_mar<TAB>` offers the host's globals, not the parked frame's locals. `rt complete print chain_mar` lists both.
- **Repeats and source position** are gdb's own; `realm-thread back` prints the frame it is back at, which moves the source position there.
- **The host is whichever thread is selected.** Switching threads from Python or MI, rather than with `thread N`, keeps the selection and shows it on the new host.
- **Cost:** every hooked command with a thread selected opens a window: reading every thread's SP, walking the registry, and writing the context, 9–19 ms per window (§3.1; about 20 ms on 16.3 for a plain command), with the test program's few threads. It wasn't measured with hundreds of threads. Installing the hooks adds 75–90 ms when realm-gdb loads.
- **The TUI** shows the host in its register window and status line, and its source and assembly windows can be left at a location that isn't current (§3.9).
- **Output that blocks keeps the window open.** A plain command prints as it goes, with its window open, so the window lasts as long as its output takes to write: with the terminal stopped by Ctrl-S, or `set logging` to a FIFO nobody reads. `rt`, which collects the output and prints it once the window is closed, doesn't have this (§8.2).

### 8.4 What a shown parked thread doesn't show as it is

- **Thread-local variables** (`fs_base` on x86-64, `tpidr` on aarch64) are the host's, in windows and core-file views alike. `print` or `set var` of one reads or writes the host's copy, with no note.
- **Registers the saved context doesn't hold** (caller-saved ones, dead at the resume PC) show the host's values in frame #0: `info registers`, `p $r10`, `p $xmm0`.
- **`$_thread`, `$_gthread`, `$_siginfo`** and `thread`'s output are the host's. Writing `$_siginfo` in a window (`rt print $_siginfo.si_signo = 11`) changes the host's own, for good, with no note.
- **Inline frames, on the host afterwards** (reproduced on 9.2 and 16.3; `window_inline_entered`). If the host stopped at the start of an inlined call, gdb shows the call as not entered yet, so that `step` steps into it (after a `step` to the call's line, or at a breakpoint on it). gdb forgets that once the thread's registers are written (`inline-frame.c` drops its state when the PC changes), as every window writes the host's, `thread apply all bt`'s included: afterwards the host's `bt` shows the inlined function as frame #0, and its next `step` starts inside it, a line further on. Python can't give gdb that state back. realm-gdb tells the case (`_skipped_inline`: the blocks at the PC that start there, before the frame's own function), says so after the command, and keeps the frame the user had selected the same frame (`_KeepSelection`).
- **A selection is checked by comparing saved contexts.** A user thread that ran and parked again with an identical context isn't noticed, nor is a `UserThread` freed and reused at the same address with the same context. Either way it is shown as it now is, but its remembered frame may then name a different frame.
- **Core files** keep the wrong frame #0 values of §4, show aarch64's d8–d15 as `<optimized out>`, and have the Python frame printer's cosmetic differences (§4). On gdb 10.2 only, `realm-thread N`, `frame 2`, then `realm-thread`, `realm-thread apply` or `thread apply all bt` print gdb's warning "Couldn't restore frame #2 in current thread" (twice for `realm-thread`), though realm-gdb then selects frame #2 again; gdb's own `info threads` prints it too (reproduced; not on 8.2, 9.2, 11.2 or 16.3).

### 8.5 `rt` and `realm-thread apply`

- **Their output is collected** and printed when the command is over (§3.4); the warnings that closing the window gives come after it, with the notes. Ctrl-C quits the command on gdb ≥ 10, as without a window, and `realm-thread apply all` then stops at the next parked thread, printing what it collected and the notes first; the interrupted command's own output is lost. On gdb 8.2 and 9.2, and after one of the command's calls has ended, Ctrl-C is held until the command is over (`window_interrupt_command`, `window_interrupt_held`).
- **Their output is unstyled before gdb 17:** gdb collects it as plain text; gdb 17's `gdb.execute(..., styling=True)` keeps it (§3.8). Nor is it wrapped at the terminal's width, as gdb wraps a long frame line before its `at FILE:LINE` (verified on 9.2 and 16.3).
- **Commands that switch gdb's output** (logging, the TUI) are refused in them (§3.8). `with logging enabled ...` in a user-defined command run there, or built by a formatted `eval`, isn't seen, and gdb 13 to 17 then crash as the output is printed; plain gdb does too.
- **An internal error in a core file's `realm-thread apply`,** whose output is collected but which opens no window, still kills gdb 12 to 16 (§3.4), as without realm-gdb; there is no program to lose (reasoned).
- **WARNINGs go to gdb's stderr,** realm-gdb's other messages to stdout: so `-batch-silent`, which silences stdout, still shows them, the warning that an attached program is killed as gdb lets go of it among them (`warnings_to_stderr`).
- **Reading the terminal by other ways** than gdb's, Python's `input()` and `sys.stdin` (`rt python` with `getpass`, `open('/dev/tty')` or `os.read(0, N)`), waits with the window open, and `os.read(0, N)` takes the user's next typed line, and the next command's first word with it (verified on 17.1). Ctrl-C ends such a wait on gdb ≥ 10, where it is let through for `rt`'s command (reasoned: it was held when the wait was seen). `rt dump binary memory FIFO ...` waits with the window open to open a FIFO nobody reads; plain gdb can't be interrupted there either. (gdb 17.1 refuses to `source` a terminal or a FIFO.)
- **Repeats:** an empty line repeats the whole `rt` line, so `rt x/2gx $sp` then Enter shows the same address again, while plain `x` continues. `rt list` continues, as gdb's listing position is global.
- **Queries take their default answers:** `rt delete` deletes every breakpoint without asking, and `rt handle SIGINT pass` changes `handle` without gdb's "Are you sure?", for good (§3.8).
- **Arguments in the C locale:** gdb can't pass non-ASCII arguments to them (§3.8).
- **`rt pipe COMMAND | SHELL`** starts SHELL after COMMAND, not alongside it, and refuses a `pipe` with no COMMAND (§3.8).
- **`thread N` inside them** selects thread N for the rest of that parked thread's command, but the next parked thread is shown on the host again, and the selection afterwards is the host (§3.1).
- **`[Switching to inferior N ...]`** follows `realm-thread` and `thread apply all bt` in an inferior with no thread (no process yet), from gdb's own notification as realm-gdb switches back to it with `inferior N`, the only way back to an inferior with no thread: they read the other inferiors' registries through their threads.
- **Selection notifications:** `thread N`, and before gdb 9 `frame function`, `frame address` and `frame view`, print from gdb's selection notification even inside a window (§3.8). That output goes to the console rather than the collected output (with `-s`, a frame line without its header), and under MI it becomes `=thread-selected` naming a parked frame.
- **`explore`** fails at its first question, since commands that read the terminal are refused there (§3.8).
- **`rt compile code ...`** runs the compiler, another program, with the window open (its calls are protected as any are).
- **`frame view ADDR PC`** with a thread selected: the next command starts again at frame #0 of the parked thread, not at the view gdb would keep.
- **Commands that read the lines after them,** and `watch` without `-l`, are refused (§3.8). Their lines are read first at a terminal, but not from a pipe (an IDE's console, say), where they still run as gdb commands after the refusal.

### 8.6 Front ends

- **IDE call-stack panes** (MI, DAP) don't show parked threads. Only console commands do: `-interpreter-exec console` and DAP's REPL.
- **DAP requests during a window's call.** DAP serves its requests as posted events, which gdb runs in the event loop it runs during a call, as it runs a second UI's commands (§3.4). The commands they run are still guarded, and Python's `gdb.execute_mi` is wrapped, but realm-gdb doesn't refuse calls in DAP sessions as it does with a second UI, so a request such as setVariable, sent while `rt print f()` runs, would run with the window open (reasoned). gdb 14.2 to 17.1's DAP makes that mostly moot: it serves one request at a time (its `main_loop`, and `send_gdb_with_response`, which waits for each), so only `cancel` comes during a call (§3.4).
- **MI notifications from windows.** MI sessions see `=cmd-param-changed` for the settings a window changes, set and put back, about ten for each window even with no call, and `=breakpoint-modified` when a call in a window disables breakpoints.
- **gdb 18 under MI** returns captured output as MI stream records, and realm-gdb decodes any line that matches one exactly (§3.6). A genuine output line of that form, from `echo ~"x"`, say, would be decoded too.

### 8.7 Noise and version mixing

- **`apropos`** lists realm-gdb's hooks (some 340 on gdb 16.3), and `show user` shows their bodies; completion and `help` leave them out (§3.6).
- **Abbreviations that only a hook's name completes** (`detach h`, `kill h`, `delete h`, where no subcommand starts with `h`) run realm-gdb's hook, with gdb's warning that it is deprecated, rather than fail as unknown; and `set hook = 1`, for a program variable named `hook`, is ambiguous (`set var hook = 1` works). Reproduced before realm-gdb kept the abbreviations of real subcommands (§3.6), which these aren't; reasoned since.
- **`set trace-commands on`** echoes each hook around every hooked command (`++realm-gdb-guard backtrace`). realm-gdb takes the echo of its own commands off what it reads of their output (`_untraced`): a user's hook kept at load would otherwise get it as a line of its body, after which `continue` and `quit` failed (`user_hook_traced`).
- **`save user FILE`** (gdb 18) writes realm-gdb's hooks into FILE too. Sourced in a session without realm-gdb, they make `break`, `run`, `bt` and `continue` fail with `Undefined command: "realm-gdb-guard"`.
- **debuginfod:** its first "Enable debuginfod?" query, should it come inside a window, would take `confirm off`'s "no" for the session, and its downloads (a source file for a frame line, say) run with the window open. It normally comes as the program loads, before any window.
- **Ada's `task N`** switches threads, and isn't taken as `thread N` is (§3.9). Untried.
- **gdb 8.2: Enter after a failed plain command** repeats one of the `set` commands realm-gdb ran at the prompt as it closed the command's window, which prints nothing, rather than the failed command: before gdb 10, a command that Python runs at the prompt becomes the one an empty line repeats. 9.2 repeats the failed command, as gdb does without realm-gdb (checked at a terminal on 8.2, 9.2, 10.2 and 17.1).
- **gdb 8.2** keeps a window's vector and x87 registers in convenience variables (`$_realm_gdb_saved_0_xmm1` and the like), which then show in `show convenience`.
- **Programs started from a Python `threading` thread** started once realm-gdb has loaded (an extension's background build, say) inherit SIGINT blocked, through `exec`, outside windows too, so Ctrl-C at the terminal doesn't reach them (§3.4; reproduced). Python's `_posixsubprocess` runs no hook as it forks, so the block can't be taken off there.
- **Mixed versions:** loading an older realm-gdb.py after this one, from a second librealm of an older build, say, mixes versions: the newest load's code runs with the hooks the older one defines. Older guards refuse any hooked command inside a window, so with this version's plain-command hooks still defined, `rt print` would be refused (reasoned).

### 8.8 Untested

- aarch64 outside CI. CI runs it (Ubuntu 24.04 and 26.04, §6.5), but PAC and SVE hardware, and the fallback register list before gdb 10, aren't covered there.
- FreeBSD on aarch64, and FreeBSD's gdbs other than its packaged 15.1. FreeBSD's `thr_kill2` path (§3.3, §3.7) runs only in CI.
- Remote targets (gdbserver), rr, and cross-architecture debugging. Losing the connection to a remote target in the middle of a window would leave the program as gdb dying does (§8.2).
- Distribution-patched gdbs other than the CI containers'. realm-gdb tells some gdb bugs by the features that came with their fixes (`_SIGINT_IN_PYTHON_SAFE`, `_COMMANDS_QUIT`, `_SIGINT_MAIN_THREAD_ONLY`, §3.4): a gdb 8.2 or 9.2 with those Python features backported, but not the fixes, would be taken for one that has them.
- Front ends that drive gdb's console (Emacs's `gud-gdb`, for example). Annotations (`gdb -f`) were checked by hand.
- Guile: no gdb at hand was built with it, so `rt guile`, `guile-repl` and the like are untested.
- Python without ctypes, where SIGTERM and SIGHUP are only blocked on gdb's main thread (§3.4), and realm-gdb can't set `PTRACE_O_EXITKILL` or stop a host before it runs (§3.7), stop a call that runs too long (§3.3), nor stand in front of Python's SIGINT handler (§3.4).
- Programs with hundreds of threads (§8.3, cost).
- GPU builds and distributed runs.

### 8.9 FreeBSD

FreeBSD x86-64 is tested in CI on FreeBSD 15.1 (§6.5), with its packaged gdb 15.1 and its own clang; 14.5 was tested in a VM here.

- **Frame #0 of a parked thread is libc's `_swapcontext`,** an assembler stub, then libthr's `__thr_swapcontext`, then `user_switch`, frame #2. FreeBSD's `swapcontext` is a system call, so the kernel saves the context inside them. gdb shows every thread blocked in a system call there the same way: frame #0 in assembler, where gdb's `language auto` parses expressions as assembler's, so a C++ expression needs `frame 2` first.
  - realm-gdb can't show `user_switch` as frame #0 instead. The stack below its frame is in use until the thread resumes, and a call made in a window goes below frame #0's SP: writing `user_switch`'s registers in, as glibc's stub is handled on aarch64 Linux (§3.2), made calls write over `__thr_swapcontext`'s frame, and the program crashed when the thread resumed. Selecting frame #2 to start with doesn't do either: `set var $pc = X` there writes the saved return address on the stack, which lasts.
- **Non-stop mode:** FreeBSD's native target in gdb doesn't support it, so `non_stop` skips.
- **Function calls at a syscall catchpoint's stop** make the system call with the call's arguments, plain gdb's too, so windows refuse them there (§3.3). FreeBSD gives no siginfo at such a stop, so it is seen from gdb's stop events, which give Python catchpoints from gdb 13: before that, or if the script was loaded after the stop, it isn't seen.
- **Call timeouts don't work** on FreeBSD's native target in gdb 15.1, which isn't asynchronous: realm-gdb's own deadline stops a window's call (§3.3, `window_call_timeout`). Without `/proc` it can't see that the call's thread has just stopped, so a deadline firing in that instant would leave a SIGINT stop for later (reasoned).
- **A host is stopped before it runs** with `thr_kill2` (§3.7), told by its siginfo's `SI_LWP`: `window_bypass_stopped` passes in CI's FreeBSD jobs.
- **`kill` right after attaching hangs gdb 15.1 on FreeBSD** (14.5 and 15.1 alike, checked with a small threaded program, without realm-gdb): the program runs on unkilled, and gdb waits in `wait4` for it to end. `ktrace` shows only `PT_KILL` and then `wait4`, with no resume in between; the program's threads are left sleeping, traced but not stopped. This is gdb's or the kernel's, and happens with no window ever shown (`gdb -p PID -batch -ex kill`). It goes away once the program has run since the attach (a `stepi`, or `continue` to a breakpoint). realm-gdb works around it only for its own kill (§3.6); a user's `kill` there still hangs, until the program ends by itself, or gdb is killed (the kernel then kills the program, §3.7).
- **gdb 15.1 can't read clang's locations for `double`s** (`DW_OP_deref_size 16`), on any thread, so `apply_callee_saved_fp` skips. realm-gdb's frame filter (core files) prints a local it can't read as gdb's own printer does, `<error reading variable NAME (...)>`, rather than let gdb's Python frame printer end the frame's locals at the error (`marker_like_native`).
- **No `/proc`:** gdb's command line comes from `ps`, and neither a second terminal nor a Python thread that doesn't block SIGINT can be seen (§8.2). The tests that read the host's registers from `/proc/PID/task/TID/syscall` (`select_external`, part of `terminal.plain`) skip that part.
- **Other skips:** `checkpoint` and `record full` don't exist for FreeBSD targets. The harness finds where the kernel writes core files from `kern.corefile` (`%N.core`), so the `kcore` tests run.
- **Realm itself** differs there:
  - `backtrace()` is in libexecinfo, which `CMakeLists.txt` links (`FindBacktrace`);
  - `KernelThread::detect_static_tls_size` detects nothing, as libthr doesn't put static TLS on thread stacks (detecting it started threads on stacks of a few KiB, and one crashed as it exited, as libthr loads the unwinder then);
  - `SharedMemoryInfo::create` uses the POSIX calls, as on Linux and macOS;
  - a user thread's stack isn't mapped with `MAP_STACK`, which on FreeBSD is a region that grows down and must be mapped readable and writable, where the stack is mapped `PROT_NONE` first;
  - `alloca.h` doesn't exist there (`tests/machine_config_test.cc`, `tests/gdb/realm_gdb_test.cc`).
- **The CI jobs** boot FreeBSD's own VM image in QEMU, with KVM, on an Ubuntu runner (`freebsd-vm.sh`), and reach it by ssh. The `vmactions/freebsd-vm` action does the same, but the repository's allowed actions don't include it.
